## 1. 두 모델에 대해 확인된 사실 (설계 제약)

### Jev (TypeSafe AI, Jev 1.13)
- **입력**: 텍스트/JSON만 받는다. 공식 문서에 "No image, audio, or video input"이라고 적혀 있다.
- **컨텍스트**: 요청 전체 64k 토큰, 상태 + 가장 긴 질문 32k 토큰.
- **출력 형태**
  - Choice: 보기 최대 255개, 보기별 확률과 confidence를 준다.
  - Score: 순서 있는 2~10단계.
  - Noul: 예/아니오 확률. confidence는 없다.
- **여러 질문 병렬**: 한 요청에 여러 질문을 넣으면 한 번의 병렬 패스로 답한다. 요청당 최대 질문 수는 확인하지 못했다.
- **접근**: 대기자 명단이 폐지되었다(9/20~21, 공식 X). 직접 API `api.typesafe.ai/v1/systemone`, 또는 OpenRouter alpha Decisions 엔드포인트.
- **비용**: 입력 $0.042/1M 토큰, 출력 무료.
- **지연**: 70~500ms. 업체 수치이며 독립 측정은 없다. 실제 제어 루프 경험치는 2~10 Hz라는 보고가 있다.
- **공식 약점 문서(jaggedness)** ★
  - 수치 정밀도, 수치 비교, 산술에 약하다. 날짜를 순서 있는 양으로 읽지 못한다.
  - 상태에 관련 없는 내용이 늘면 정확도가 떨어진다.
  - 공식 권장: 산술, 기하, 시간 비교는 코드에서 하고 임계값을 명시한다.
  - → 원좌표를 그대로 주고 판단시키는 설계는 위험하다(M1, M3에 반영).
- **보정(calibration)**: 업체 주장(RLCD)뿐이다. 논문과 보정 곡선이 공개되지 않았으므로 **우리 데이터로 직접 측정**해야 한다.
- **벤치마크 67.8%**: 정답 대비 정확도가 아니라 Astra/Fable 평균 예측과의 **일치도**다.
- **프롬프트 인젝션에 취약**하다(공식 문서, VentureBeat).

### GPT-6 Astra (OpenAI, 2026-09-03 출시)
- **입력**: 텍스트 + 이미지. 비디오 입력 지원 근거는 없다. → 연속 프레임은 여러 이미지나 격자 한 장으로 넣는다.
- **컨텍스트**: 1.05M 토큰.
- **가격**: $10 입력 / $50 출력 (1M 토큰).
- **첫 토큰까지 시간** (Artificial Analysis 측정)
  - effort low 2.8초 / high 45초 / max 250초
  - → effort 선택 자체가 설계 변수다.
- **로봇 결과는 모두 제3자 평가다** (OpenAI 공식 로봇 결과나 API는 없다).
  - Robocurve: 양팔 로봇, 블록→그릇 19/20, 정밀 삽입 2/20.
  - RoboDojo(arXiv 2609.24170, 미심사): 42개 작업 평균 성공률 22.5%.
  - "휴머노이드 zero-shot"이라는 기사는 오보다. 실제로는 양팔 로봇이다.
- 정밀 실행이 약하다는 점은 "정밀 실행은 하위에 맡긴다"는 우리 구조의 동기를 뒷받침한다.

## 2. 모듈별 장착 후보 (v2)

### M1. 상태 표현: 이미지 → Jev 입력
- [사용자] AI 전 분야에서 가장 효율적인 방법을 쓴다.
- [제안] **인식 앞단**
  1. SAM 3 / 3.1 (HIGH, ICLR 2026, Meta): 텍스트 프롬프트 하나로 검출, 분할, 추적을 하고 ID를 유지한다. 깊이와 결합하면 3D 위치를 얻는다. 개방어휘라 일반화 메시지와 맞는다.
  2. FoundationPose (HIGH, CVPR 2024) 또는 Any6D (HIGH, CVPR 2025): 자세가 필요한 작업용이다. 초기화 약 1.3초, 추적 약 32 Hz이므로 별도 고속 루프로 돌린다.
  3. YOLOE (HIGH, ICCV 2025): 더 빠른 대안.
- [제안] **표현 형식** (v1 수정)
  - 작업에 관련된 물체만 넣는다(관련 없는 내용은 Jev 정확도를 떨어뜨린다).
  - 좌표 같은 수치는 코드에서 미리 계산해서 **범주화한 관계**로 준다. 예: "목표가 그리퍼의 +x 방향, 거리 구간 3/5". 원좌표는 보조로만 둔다(Jev 수치 약점).
  - 참/거짓 술어를 둔다: `grasped`, `above_target`, `in_contact` 등.
  - ~~diff만 주기~~: 근거가 없어서 v2에서 뺐다. 절제 실험 변수로만 둔다.
  - 근거: BALROG(ICLR 2025, 텍스트 결정 > 이미지 결정), SiT-Bench(ACL 2026 Findings), RoboPrompt(텍스트 자세로 행동 예측), GSU(자기 기준 좌표계 약점 → 미리 계산할 필요)
- 형식 민감도가 크고 모든 경우에 최선인 형식은 없다. **Jev로 직접 실험해서 정한다.**
- [결정 필요] 인식 앞단 확정 (CLAUDE.md 규칙상 사용자가 정한다)

### M2. Astra → Jev 전달
- [사용자] M1과 같은 문제로 본다.
- [제안]
  - 1순위: **완료 조건 술어 집합 + 대상 물체 ID + 예상 소요 시간 + 허용 동작 범위 + 연결할 스킬**
  - 키포인트 관계(ReKep)는 원래 Python 비용 함수다. Jev에는 "제약을 만족하는가"라는 술어로 바꿔서 넘긴다.
  - 이정표 상태는 개념만 쓴다. v1의 근거였던 B2FF는 신뢰도가 낮고 이미지 기반이라 뺐다.

### M3. 행동 표현 (촘촘한 객관식)
- [사용자] 촘촘하게 가도 된다.
- [제안] (v1 수정)
  - 크기는 **순서형 보기**로 준다(Choice나 Score).
  - 확률 가중 평균은 분포가 한 봉우리일 때만 쓰고, 그 외에는 최빈값을 쓴다. 여러 봉우리 분포를 평균하면 엉뚱한 동작이 나온다(RTC 논문 지적).
  - 스텝별 단일축 Choice(원안)와 **저주파 경유점/제어점 Choice**(FAST의 관찰을 참고)를 비교 실험한다.

### M4. 연속 동작 1단계: 계단식 겹침 호출 + 자기 검증 ★
- [사용자] 1초에 여러 번 계단식으로 겹쳐 호출하고, 겹침 구간이 제대로 반영됐는지 스스로 확인하고 업데이트한다. 가장 중요하다. RTC를 참고한다.
- [제안] 장착 후보 (모두 학습 없이 쓸 수 있는 형태로 가져온다)
  1. **큐 임계값 비동기 스케줄러 + 확정 앞부분 고정**
     - SmolVLA 비동기 추론: HIGH, Hugging Face LeRobot
     - RTC: HIGH, NeurIPS 2025, Physical Intelligence
  2. **응답 도착 시점의 예상 상태를 입력으로** (VLASH 발상, MED-HIGH, MIT Han Lab): v1에 없던 핵심 보완이다. Jev 응답 지연 동안 로봇이 움직인 만큼을 반영한다.
  3. **겹침 구간 융합 규칙**: 이전 선택과 새 선택을 기하 유사도 × 지수 감쇠로 섞는다(Slow Brain Fast Planner, arXiv 2606.20458, MED).
  4. **매 제어 스텝 도는 빠른 기하 보정층** (A2C2 발상, MED-HIGH): v1의 "다음 호출에 보정"은 느린 루프라서 빠른 루프가 따로 필요하다.
  5. **일관성 기반 선택** (BID 발상, HIGH, ICLR 2025, 기간 밖이라 개념만): Jev 확률 × 이전 조각과의 일관성으로 고른다.
  6. 겹침 불일치 크기 → M7/M8 이상 신호. Sentinel의 STAC(일관성 신호)와 같은 역할이다.
- 선행 연구 정정: 토큰 기반 정책의 실시간 실행(2606.13355), 느린 VLM 선택을 실시간 계획기에 섞는 연구(2606.20458)가 이미 있다.
  - → 컨트리뷰션은 "**객관식 결정 모델의 계단식 겹침 + 확률 기반 자기 검증 업데이트**"로 좁힌다.

### M5. 연속 동작 2단계: 스무딩
- [사용자] 두 단계로 나눈다. 2단계는 스무딩이다.
- [제안]
  1. LiPo식 후처리: 겹침 선형 블렌딩 + jerk 최소화. 학습이 필요 없는 확인된 선택지다(MED).
  2. B-스플라인 제어점 표현(M3와 공유).
  3. 기준 방법: temporal ensembling(ACT), 지수 평활.
- 뺀 것(LOW): ABPolicy 외 5개.

### M6. 스킬과 Jev 결합
- [사용자] 잘게 엮는다. 1년 이내, 스타 상위 논문을 참고한다.
- [제안]
  1. **CaP-X** (HIGH, ICML 2026, Goldberg, Fei-Fei, Yuke Zhu, Jim Fan, 약 800★ 단일 출처)
     - 추상화 수준별 스킬 API, 여러 번의 실행 피드백, **장면 변화를 텍스트로 설명하는 모듈(VDM)**, 스킬 자동 합성.
     - 생성 코드 안에 "typed 선택 함수"로 Jev를 넣는다.
  2. **ASPIRE** (MED, NVIDIA GEAR, preprint): 실패 진단 → 수리 → 검증 → 스킬 저장. LIBERO-Pro Long에서 31% 대 4%.
  3. RoboOS(창 밖, 개념만), ROSClaw(LOW-MED, 실행 전 예/아니오 검증 자리)
- "스타 상위 5개" 순위는 스타 수를 확인할 수 없어서 아직 확정하지 못했다.
- 뺀 것: VLCP(LOW), Agentic Robot(창 밖이고 VLA 실행기).

### M7. 진행 판별 ("계획대로"의 정의)
- [사용자] VLA의 개념을 많이 참고한다.
- [제안]
  1. **센서와 술어로 완료를 판정하고, 진행도는 "완료까지 남은 시간"으로 정의한다** (RECAP 개념, HIGH, PI).
     - 접촉과 파지는 VLM이 약하므로 센서로 본다(FailBench: 접촉 작업 0.60 이하, 애매하면 "성공"으로 치우침).
  2. **SAFE의 conformal 시간 가변 임계값** (HIGH, NeurIPS 2025): 점수 모델은 빼고 임계값 방법만 Jev 확률에 붙인다.
  3. **Astra로 가끔 GVL 방식 진행 확인**: API 모델에서 TOPReward보다 나았다.
- v1 수정: TOPReward는 비디오 VLM의 logit을 써서 Jev와 맞지 않는다.
- 학습형(VLAC, ProcVLM 등)은 일반화 메시지와 충돌한다. VLAC는 비교 기준 방법으로만 쓴다.

### M8. Astra 호출 시점과 다중 프레임
- [사용자]
  - 최소한 실패 판정이 나면 부른다. 연속 프레임을 준다.
  - 호출 방식 3가지(주기 / 정한 순간 / 예상 시간 초과)를 비교 평가한다.
  - 처음 계획할 때만 멈추고, 이후에는 웬만하면 멈추지 않는다.
- [제안]
  - 1순위: 이벤트 호출(M7의 실패/정체 판정, 예상 시간 초과). 근거: Sentinel-VLA(HIGH, ICML 2026), FPC-VLA(MED)
  - **Astra effort를 호출 목적별로 나눈다**: 처음 계획은 high(정지 허용), 복구나 주기 호출은 low 또는 fast mode. 비교 실험 축에 effort를 추가한다.
  - 격자 한 장 대 개별 이미지는 증거가 엇갈려 실험 항목으로 둔다(v1의 Guardian 인용은 시간 축이 아니라 카메라 시점 축이었다).
- 세 호출 방식의 정량 비교가 없다는 주장은 아직 **확인하지 못했다.** 다음 조사에서 arXiv 2608.28075(event-triggered FM planning)를 먼저 확인한다.

### M9. 실패 복구
- [사용자] VLA에서 가장 좋은 방법을 찾는다.
- 사실: 복구 방법끼리 직접 비교한 벤치마크는 없다. "최고"는 정해지지 않았다.
- [제안]
  1. **FLARE의 재시도/리셋 구조** (HIGH, CVPR 2026): Gemini-2.5-Pro가 영상을 보고 재시도와 리셋 스킬 중에서 고른다. 분류 정확도는 88%, 96%다. Astra + 스킬 구조에 그대로 맞는다.
  2. **FailSafe의 복구 행동 출력 형식 + 실패 자동 생성**(평가용 실패 주입) (MED, UW/AI2)
  3. **AHA식 실패 설명**을 Astra 재계획 입력으로 쓴다 (HIGH, ICLR 2025, 창 밖이라 허용이 필요하다).
  4. FAR은 개념만 쓴다. 실제로는 정책 업데이트가 필요하다(v1 설명이 틀렸다).
- v2 복구 사다리 [제안]: Jev 재시도 → FLARE식 리셋 스킬 → Astra 재계획(다중 프레임 + 실패 설명)
- 뺀 것: B2FF 외(LOW).

### M10. 경험 축적
- [사용자] API 모델 기반의 경험 축적을 제대로 한다.
- [제안]

# L9 v2 bimanual datagen -- implementation design (2026-10-02)

Owner-approved source: `docs/research/bimanual_datagen_2026-10-02.md` (dev fce3eee), 40 definitions, categories A-F.
This note is the engineering plan for category A (handover) first, on top of the EXISTING single-arm L9 v2 stack
(`rt9.Runtime`, `plan9_server.PlannerProxy`, `v2plan.plan`, `task9`/`task9v2`), not a rewrite of it.

## 1. What already exists (read before writing code)

- `harvest/sim/scene.py` `SimEnv.__init__(..., dual=False)` (b2b8946, opt-in): with `dual=True` the action space is
  `[arm, grip, arm2, grip2]` (both arms' joints + both widths every physics step). `env.use_arm(arm)` swaps the
  *readout* context (`arm_ids`, `ee_idx`, `finger_idx`, `grip_id`, `tcp_offset`, `finger_slice`, ...) so `arm_q()`,
  `ee_pose()`, `finger_mid()`, `gripper_width()` and the contact filters report whichever arm is current.
  `env.set_arm2_target(q, width)` stores the OTHER arm's target (used automatically by the next `env.step()`); the
  `arm=` kwarg at construction fixes which arm is `env.primary` -- `env.step()` refuses to run unless
  `env.use_arm(env.primary)` was called first (`"dual: step() takes the primary arm's targets"`). Primary is **fixed
  per process/episode**, it cannot be swapped tick to tick.
- `harvest/l9/curobo9.py`: a profile's per-arm cuRobo config (`assets9/curobo/<robot>_<arm>.yml`) already has the
  OTHER arm's 7 joints in `lock_joints` (checked `ffw_sg2_right.yml`: `arm_l_joint1..7` locked, cspace has all 23
  joints of the full robot). `with_locks()` can rebuild the solver with the other arm's *live* joints baked in, but
  the maintainer warns v0.8.0 bakes locks into the solver at build time -- a new value needs a new solver. Rebuilding
  per planning call is too slow for a datagen lane. Decision (matches the research doc's own recommendation and the
  cuRobo maintainer note): do **not** rebuild the solver per call. Instead treat the other arm as a plain obstacle
  cuboid (same mechanism `rt9.Runtime.refresh_world` already uses for scene objects), sized around its current TCP /
  forearm segment, added to `planner.world(scene)` before every plan. This is approximate (not a true self-collision
  check against the other arm's real links) and is the single biggest correctness risk of the whole feature --
  logged as risk R1 below, to be checked against the recorded wrist videos at the pilot gate.
- `harvest/l9/rt9.py` `Runtime` is a complete, heavily-tuned single-arm "device driver": `choose()` (grasp candidate
  selection), `plan()` (truth step state machine, called by `teach_l8d.xlabels.plan` once hooked), `motion_for()`
  (cuRobo planning + guards), `TrajExec` (joint-trajectory executor matching the `MinJerkExec` interface). It is
  keyed to ONE `world` + ONE `arm` and is otherwise self-contained (every geometry read happens through
  `self.w.env.*`, scoped by whichever arm is current). **Decision: reuse `Runtime` unmodified, one instance per
  arm**, instead of writing a second planner. The bimanual-specific code only needs to (a) call `world.env.use_arm`
  before touching either Runtime's world-scoped state, (b) feed physics steps to the dual env, (c) add the
  handover-specific timing gate (receiver does not close until the giver is in the zone; giver does not open until
  the receiver has closed).

## 2. Runtime structure (`harvest/l9/bimanual9.py`, new module)

Pure layer (no Isaac/torch import, unit-tested on the laptop):
- `BIM_A_DEFS`: the 12 category-A definitions (6 object groups x 2 directions) as plain dicts
  `{cats, giver, receiver}` -- NOT routed through `task9.TaskDef`/`task9.instantiate()`'s destination-spot sampler,
  because the handover zone is a robot-geometry point, not a furniture/table node (the research doc's own framing,
  §(d).3). `task9`/`scene9` are still used, unmodified, for everything they are already good at: drawing a valid
  scene and a start pose for object A reachable by the giver arm (reusing an existing single-object TaskDef, e.g.
  `task9.DEFS["set_centre"]`, filtered to the right category -- the destination that definition samples is ignored).
- `handover_zone_xyz(profile, table_z)`: **hypothesis** (flagged, matches the research doc's explicit "가설" tag) --
  world-frame point roughly at the shared midline in front of the robot, above the table (not resting on it, so the
  "no floor/table contact" success check is meaningful): `y = 0` (the AI Worker's left/right arms are mirrored about
  y, `arm.py`), `x` inside both arms' measured top-down band (`scene.WS_X/WS_Y`: x in [0.36, 0.48]), `z = table_z +
  0.20`. R1 Pro / G1 use the same formula with their own `robot9.V2[profile]["arms"]` reach bands; unvalidated for
  those two (category A ships AI Worker first per the owner's plan step 3).
- `bim_command(arm, role, position_m, gripper, quat_wxyz, sync, point_px=None, height=None, approach=None,
  wrist_bin=None)`: the minimal extension of the existing per-arm command (`v2plan.plan`'s `position_m`/`gripper`/
  `quat_wxyz`) with the three new fields from the research doc §(d) schema: `role` (`lead|support|independent`),
  `sync` (bool), and `gripper` gets a third value `"hold"` (closed, contact-maintained, no new grasp attempted --
  used by the giver while it waits at the zone). The existing `views9.ARM_NOTE` text ("a call may give one command,
  or two as `commands`: [one per arm]") already describes multi-arm calls; nothing there needs to change, only the
  per-command dict gains `role`/`sync` keys and the `gripper` enum gains `hold`.
- `handover_phase(phase, giver_at_zone_holding, receiver_contacted, giver_opened, receiver_holding)`: pure FSM,
  7 phases: `giver_pick -> giver_carry -> giver_hold -> receiver_pick -> giver_release -> receiver_carry -> done`.
  `giver_hold -> receiver_pick` only once `giver_at_zone_holding`; `receiver_pick -> giver_release` only once
  `receiver_contacted` (both-closed overlap, §(c) success criterion); `giver_release -> receiver_carry` once
  `giver_opened`.
- `success_a(final_xy, target_xy, tol=0.03, floor_touched=False, overlap_ticks=0)`: the category-A gate from the
  research doc §(c): overlap_ticks >= 1 (both closed at once), no floor contact during the whole transfer, final
  position error <= 3 cm (pose error <= 15 deg deferred to the pilot: the laptop-side check only has xy here).

Impure layer (lazy `torch`/`curobo`/`isaaclab` imports, pod only):
- `HandoverRuntime(world, profile, giver_arm, receiver_arm, device)`: builds two `rt9.Runtime` instances (one per
  arm, constructed while `world.env.use_arm(that_arm)` is current so each one's `__init__`-time snapshots --
  `sim_ids`, `arm_ids`, `base_idx` -- are correct; after construction every `Runtime` method is self-contained via
  its own snapshot, confirmed by reading `rt9.Runtime.__init__`/`arm_q`/`tcp_T`). Drives a tick loop that, every
  physics step: `use_arm(giver)` -> read giver `st` -> `TrajExec` tick -> compute giver's 7-DOF target + gravity
  offset (same formula as `rt9.install`'s `step()` monkeypatch) -> `use_arm(receiver)` -> same for receiver -> build
  the receiver's 7-DOF action, call `env.set_arm2_target(q_receiver, width_receiver)` -> `use_arm(env.primary)` ->
  `env.step(primary_8d)`. `env.primary` is fixed per episode (the env's `arm=` constructor kwarg); for an L->R
  handover def the env is built with `arm="left"` (so the giver is primary) -- direction therefore decides which
  physical SimEnv process is used, matching the existing one-arm-per-process convention (`run9.py`: "one arm per
  process").
- Per-tick "other arm as obstacle": before each arm's `planner.pose()/line()` call, in addition to
  `Runtime.refresh_world()`'s own object cuboids, add one box centred on the other arm's current TCP (half-extents
  ~ gripper + 6 cm pad, a coarse but cheap stand-in for the whole hand) into the `scene` dict passed to
  `planner.world()`. This only matters in `giver_carry`/`receiver_pick` (the only phases where both arms are near
  the zone at once) -- the pure FSM above keeps every other phase one-arm-active / one-arm-frozen, which removes
  the need for true simultaneous bidirectional planning (and most of the collision risk) for category A.
- `run_smoke(n, out_dir, profile="ffw_sg2", seed0=..., device="cuda:0")`: drives `HandoverRuntime` through N
  episodes, writing `calls/`, a `labels.jsonl` using `bim_command`, and `frames/` (head + both wrists, every
  `VIDEO_EVERY` tick, matching the existing `astra_solo.episode` convention) so the owner's "video every run"
  standing rule is satisfiable without extra plumbing.

## 3. What this note does NOT cover yet (owner should not read "designed" as "built")

- Categories B-F: not designed in code yet beyond the phase-FSM pattern above generalising to them (B/D need a
  *simultaneous* gate -- "both grippers closed before either lifts" -- which is the mirror image of category A's
  gate and reuses the same `handover_phase`-style pure FSM machinery, not new infrastructure).
- R1 Pro / G1 profiles: the zone-geometry hypothesis above is written generically but untested outside AI Worker.
- Full production label/build integration (`collect9.run_episode`, `teach_l8d.collect.collect_episode`,
  `build9.py` row construction): the smoke harness (`run_smoke`) is a standalone loop, not routed through
  `collect_episode`'s DART-perturbation + XCollector pipeline. Wiring into that pipeline is the next step after the
  smoke episodes look right in sim (owner's plan step 4, pilot gate), and is a materially sized follow-up (the
  existing single-arm `rt9.install()` hooks three separate modules to do this; the bimanual case needs an analogous
  hook set that can carry TWO commands per call through to `build9`'s row format).

## 4. Risks (numbered to match the research doc's risk list, continued)

- R1 (NEW): the "other arm as an obstacle cuboid" approximation (not a true dual-arm self-collision check) may let
  the two grippers graze at the handover zone in sim even though cuRobo reports a clear plan. Mitigation: the pilot
  gate's frame check (head + both wrists) is the actual test; if contact/penetration shows up, the fallback from the
  research doc (rebuild the solver with `with_locks` at a small number of discretised "other arm" poses: stowed /
  at-zone / mid-transit) is the next move, not a full per-step solver rebuild.
- R2: `env.primary` is fixed per process, so a bimanual job plan needs one row per (profile, direction) the same way
  single-arm needs one row per (profile, arm) -- `run9.py`'s "one arm per process" constraint becomes "one direction
  per process" for category A. Needs a small, separate `tools/l9/plan_bim.py` (not written yet).
- R1b (found and fixed while writing `bimanual9.HandoverRuntime`): `Runtime.choose()` / `_valid()` / `_approach_plan()`
  all call `self.refresh_world()` themselves (several times, to check IK / support clearance / the straight
  approach), which would silently overwrite whatever extra "other arm" obstacle box had been set right before --
  the other-arm-as-obstacle box would only have survived in the *carry* move, not grasp candidate selection or the
  approach transit. Fixed by adding `extra_boxes` (opt-in, default `None` = unchanged) to `Runtime.refresh_world`,
  `_valid` and `choose` and threading it through `_approach_plan`'s internal `refresh_world` calls too
  (`harvest/l9/rt9.py`); `bimanual9.other_arm_boxes()` now builds the dict once per call and every bimanual caller
  passes it through these instead of calling `planner.world()` a second time itself.
- R4 (open, found in pod smoke #2-5, 2026-10-02): the handover zone's y=0 (exact midline, spec note §2's
  `handover_zone_xyz`) gets `ik_ok=0` for the receiver's grasp candidates even after x/z were moved to
  `scene.INIT_R_ARM`'s own (known-reachable) values -- i.e. not the other-arm obstacle box (that filter runs after
  the bare IK check), a genuine cuRobo IK reachability gap at y=0 for at least one of the two arms. AI Worker has no
  `reach_map`/`reach_ok` tool the way R1 Pro / G1 do (`curobo9.reach_map`, built by `tools/l9/v2robot/reach_v2.py`);
  guessing further x/y/z combinations by hand (3 tries so far, each a 2-4 min pod round trip) is not a good use of
  further pod time. Next step: build the equivalent reach sweep for `ffw_sg2_left.yml` / `ffw_sg2_right.yml`
  (batched IK over a grid, no world obstacles, matching `reach_v2.py`'s own approach) and intersect the two arms'
  reachable sets for `(x, y, z)` -- replaces guesswork with the actual answer, and is reusable for R1 Pro / G1's
  zones too (`ZONE_X_V2` / `ZONE_Z_ABOVE_TABLE_V2` are equally unverified guesses right now).
- R3 (research doc R2, carried over): giver-open / receiver-close timing is force/friction-sensitive; the pure FSM
  only gates on *measured gripper width* (CONTACT classification, reusing `rt9.classify_close`), not force, so a
  light object could register CONTACT on the receiver before it can actually bear the object's weight. Flagged for
  the pilot's success-rate numbers to catch, not fixable without physics in the loop.

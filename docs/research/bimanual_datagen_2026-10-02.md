# 양팔 협응(Bimanual) 과제 설계 및 데이터 생성 — 문헌 조사 + 결정 (2026-10-02)

user-log 참조용 요약: 기존 253개 과제는 전부 단일팔. 상위 VLM(Qwen3.5-35B LoRA)이 머리캠 1장을 보고 호출마다 1~2개 팔 명령(픽셀점·높이·접근군·손목 회전 bin·그리퍼 의도)을 내는 구조는 유지하고, 스키마에 `arm: left|right` 두 개를 실어 진짜 양팔 협응 과제를 만든다. 초안 12개(핸드오버 6·양손 들기 3·고정+담기 2·동시배치 1) 대비 3배인 ≥36개로 확장.

## (a) 남들이 양팔 과제를 분류하는 방식 — Taxonomy

가장 널리 쓰이는 축은 두 개다 (출처: ACT-류 좌표계 논문 arXiv:2503.13916, 2025-03; PerAct2 2024-07는 날짜창 밖이라 배경 인용):

1. **동기화 축**: 비동기(asynchronous, 한 팔이 끝나야 다음 팔 시작) vs 동기(synchronous, 두 팔이 같은 시간창 안에서 움직임).
2. **협응 강도 축**: `unimanual → bimanual uncoordinated(독립, 충돌만 피함) → loosely coordinated(느슨한 시간 겹침) → tightly coordinated symmetric(대칭, 동시 동일 동작) → tightly coordinated asymmetric(비대칭, 한쪽은 지지·한쪽은 조작)`.

RoboTwin 2.0(arXiv:2506.18088, 2025-06, ICML 2026)은 이걸 실제 과제 라벨로 구현해 13개 평가 과제를 `Bimanual coord.`(핸드오버류), `Bimanual lift`(양손 들기), 단일팔류로 나눈다. PerAct2(배경 인용, 2024-07)의 13개 과제도 동일 축: handover_item/handover_item_easy(핸드오버), lift_ball/lift_tray(동기 들기), push_box/dual_push_buttons(독립·대칭), put_item_in_drawer류(비대칭 고정+조작 — 단 우리는 서랍/문 제외 지침이라 미채택).

BiGym(arXiv:2407.07788, 배경 인용, GitHub Apache-2.0·221★)은 여기에 **모바일 베이스 이동 중 양팔**이라는 세 번째 축을 추가하지만, 우리 설정은 고정 베이스 pick/place라 이 축은 생략.

정리하면 우리 문서가 쓰는 범주는 문헌 taxonomy를 그대로 투영한 6개:
- A. 순차 핸드오버 (비동기, 비대칭→대칭 전환)
- B. 양손 동시 들기·운반·배치 (동기, 대칭)
- C. 비대칭 고정+조작 (느슨한 협응, 비대칭)
- D. 동시 독립 두 물체 배치 (uncoordinated, 대칭)
- E. 손-대-손 재파지/재정렬 (동기 접촉, 비대칭→대칭)
- F. 정렬/삽입 협응 (느슨~타이트, 비대칭)

## (b) 대규모 시뮬레이션 데이터 생성 방식

**플래너/협응 방식**
- RoboTwin 2.0: MLLM이 과제별 실행 코드를 생성하고 시뮬레이션-루프 내 보정(simulation-in-the-loop refinement)으로 성공 궤적만 채택. 5개 축(혼잡도·조명·배경·탁자높이·언어) 도메인 랜덤화로 단일 전문가 궤적을 대량 변주. 양팔은 각 팔을 **독립 모션 플래너 호출 + 공유 충돌 체크**로 조합(동시 최적화가 아님).
- DexMimicGen(arXiv:2410.24185, 2024-10 / ICRA 2025, 날짜창 경계 — 투명성 위해 명시): 사람 시연 60개 → 변환+리플레이로 21K개 생성. 양팔 비대칭 과제(한 팔 보조/한 팔 리드)는 **각 팔의 서브태스크 경계를 수동 주석**한 뒤 팔별로 독립 보간·리플레이, 실패 시 팔별 재시도.
- MoMaGen(arXiv:2510.18316, 2025-10, ICLR 2026, 코드 라이선스 미확인이라 아이디어만): 데이터 생성을 **제약 최적화**로 공식화 — hard constraint(도달 가능성), soft constraint(내비게이션 중 가시성) 동시 만족. 멀티스텝 양팔 모바일 조작에서 단일 소스 시연으로 다양한 데이터 생성.
- cuRobo(≥0.8.0, Apache-2.0, 우리 스택과 동일): 공식 문서 기준 **동기(synchronous) 양팔 계획은 지원**(두 팔이 각자의 목표에 "동시 도착"하도록 계산) 하지만, 진짜 결합 최적화(한 번의 solve로 양팔 상호 제약까지 반영)는 **실험적(experimental) 기능**이라고 cuRobo 메인테이너가 GitHub Discussion #209/#438에서 직접 밝힘. 권장 패턴은 "다른 팔 관절을 잠그고 한 팔씩 계획 → 잠금 전환"이다.

**성공 판정**
- 공통적으로 **특권 상태(ground-truth pose) 기반**: 목표 위치 tolerance box 안에 물체 중심이 들어오는지, 그리퍼 접촉/힘 플래그, 낙하(바닥 접촉) 여부. 비전 기반 판정기를 쓰는 사례는 못 찾음(우리 1.5년 창 안에서는 0건) → 우리도 기존 특권 판정 인프라를 그대로 쓰는 게 근거 있는 선택.
- RoboTwin 2.0은 추가로 "두 팔이 서로 충돌하지 않았는가"를 자가충돌 로그로 별도 체크.

**실패 모드 (문헌에서 공통 언급)**
- 핸드오버 타이밍 어긋남 → 낙하 (DexMimicGen, RoboTwin2.0 둘 다 보정 루프/재시도로 완화, 정량 수치는 공개 안 함 → 우리가 튜닝해야 함, 가설 취급).
- 양팔 자가충돌로 인한 플래닝 실패/타임아웃 (cuRobo 이슈 #595 "constraint about dual arm"에서 반복 보고).
- 도메인 랜덤화 과함 → 전문가 궤적 자체가 실패해 데이터 질 저하 (RoboTwin2.0이 MLLM 보정 루프를 둔 이유).

**두 팔 행동 표현 방식**
- RoboTwin2.0/PerAct2/ALOHA류 전부 "팔별 액션 벡터를 하나의 타임스텝에 concat"하는 방식(동기) 또는 "팔 ID 태그가 붙은 서브태스크 시퀀스"(비동기, DexMimicGen)로 수렴. 둘 다 우리의 "호출당 1~2개 arm 명령" 스키마와 자연스럽게 대응된다.

## (c) 권장 양팔 과제 정의 — 40개 (요구치 36개 충족)

공통 성공 기준(범주별, ground-truth pose 기반 — (b)의 근거를 그대로 적용):
- **A(핸드오버)**: 주는 팔이 물체를 쥔 뒤 핸드오버존 진입 → 받는 팔 접촉 확정 후에만 주는 팔 오픈(둘 다 닫힌 겹침 구간 ≥1 스텝) → 전체 과정 중 바닥 접촉 0 → 최종 목표 위치 오차 ≤3cm, 자세 오차 ≤15°.
- **B(동시 들기)**: 두 그리퍼 모두 닫힌 뒤에만 상승 시작(동시 게이트) → 운반 중 물체-바닥 간격 유지 → 목표 지점 낙하지점 오차 ≤3cm → 두 그리퍼 모두 물체가 지지면에 닿은 뒤 오픈.
- **C(고정+조작)**: 고정팔 접촉/자세가 작업 내내 드리프트 ≤2cm 유지 → 조작팔의 담기/따르기/얹기 완료(물체 또는 액체 타깃 컨테이너 내부 판정) → 고정 대상 전도 없음.
- **D(동시 독립 배치)**: 두 목표 모두 각자 tolerance 안에 배치 → 양팔 간 자가충돌 0회(cuRobo self-collision 로그 기준).
- **E(재파지)**: 전달 중 낙하 0 → 받는 팔이 쥔 뒤 최종 자세가 목표 회전 bin(15° 단위) 안에 들어옴.
- **F(정렬/삽입)**: 정렬팔 유지 오차 ≤1cm → 삽입/적재 완료 후 동심/정렬 오차 ≤1cm → 해제 후 N스텝 안정(미끄러짐/전도 없음).

## (d) 권장 구현

**cuRobo 양팔 플래닝**
1. 기본값(안전): discussion #209 방식 — 두 팔을 하나의 운동학 트리(URDF, ee_left/ee_right 두 엔드이펙터)로 모델링하되, **"다른 팔 관절 잠금 → 한 팔씩 solve → 잠금 전환"**으로 순차 계획. 자가충돌 체크는 반드시 전체 양팔 트리 기준(cuRobo 문서가 명시하는 "두 팔이 서로 충돌 회피"하는 동작)으로 켠다.
2. 동기(B·D 범주, 동시 들기/동시 배치)에는 두 팔의 `num_waypoints`·`dt`를 동일하게 맞춰 공통 시간축으로 보간한 뒤, 상대 자세(물체를 쥔 두 그리퍼 간 고정 변환) 유지는 **솔버 제약이 아니라 시뮬레이션 사후 검증**으로 처리(cuRobo의 동시-양팔 결합 최적화는 메인테이너가 "experimental"이라 공식 표명했으므로 프로덕션 데이터 생성에 바로 신뢰하지 않음).
3. 핸드오버(A·E 범주) 타이밍은 2단계 스크립트 안무: (i) 주는 팔 접근+파지+핸드오버존 진입 플랜, (ii) 받는 팔은 핸드오버존 도달을 대기 상태로 미리 계획해두고 접촉 확정 신호(그리퍼 폐합+접촉 플래그) 후 폐합, 그 다음에만 주는 팔 오픈. cuRobo 자체 기능이 아니라 호출 측 오케스트레이션으로 구현.

**상위 출력(스키마) 명령 포맷 제안** (가설 — 문헌에 정확히 이 스키마가 있는 건 아니고, 기존 4개 뷰 슬롯/필드 구조를 그대로 확장한 설계안)
```
call:
  head_view: <existing>
  commands: [          # 1~2개
    { arm: left|right,
      role: lead|support|independent,   # C=lead/support, D=independent, A/B/E/F는 상황별
      point_px: [x,y],                  # 0-1000, head 기준
      height: <existing>,
      approach: top|oblique|front|side,
      wrist_bin: <15도 단위, existing>,
      gripper: grasp|release|hold,      # 'hold' 신규 — C 범주 고정팔용, 접촉 유지
      sync: true|false                  # 두 명령이 같은 시간창에서 동시 실행되어야 하는지
    }, ... ]
```
- `role=support`일 때 `gripper=hold`는 접촉 유지(자세/힘 드리프트 bound 내)를 뜻하는 새 의도값. 기존 grasp/release 두 값만 있던 걸 확장.
- A 범주 받는 팔의 `point_px`는 "주는 팔 그리퍼의 미래 위치"를 VLM이 추정하게 하지 말고, **로봇 기하학으로 사전 계산한 고정 핸드오버존 픽셀 좌표**를 항상 타깃으로 쓴다(가설/설계 권고 — 라벨링 노이즈를 줄이기 위함, 문헌 근거 없음).

**라벨링 규칙**
- 핸드오버: giver 라벨 = 물체 실제 위치, receiver 라벨 = 고정 핸드오버존(동적 추정 금지).
- 고정+조작: 고정팔 `approach`는 컨테이너 손잡이/테두리 기하에 맞춰 사전 고정(top 또는 side), `gripper=hold`로 라벨.
- 동시 독립 배치: 두 타깃이 서로의 팔 작업공간과 겹치지 않도록 **과제 정의 단계에서 사전 필터링**(라벨링이 아니라 과제 설계 시점에 배제) — 자가충돌로 인한 플래닝 실패율을 낮추기 위한 설계 휴리스틱(가설).
- 재정렬(E): 최종 회전 bin은 손목 회전 bin 해상도(15°)에 맞춰 양자화해서 라벨.

**리스크**
1. cuRobo 동시 양팔 결합 최적화가 실험적 기능 → 프로덕션 규모에서 플래닝 실패/퇴화 궤적 위험. 완화: 기본은 순차 잠금 방식, 동시 solve는 검증 후에만 opt-in.
2. 핸드오버 접촉-해제 타이밍이 물리 파라미터(마찰, 그리퍼 강성)에 민감 — 문헌이 정확한 수치를 공개하지 않아 우리가 직접 튜닝해야 함(가설 구간).
3. G1(Dex3-1 손)과 AI Worker/R1 Pro(평행 그리퍼)의 그리퍼 의도 어휘가 동일하지 않을 수 있음 — embodiment별 파지 프리미티브 매핑 계층 필요(통합 검증 필요).
4. 두 팔이 한 작업공간을 공유 → 자가충돌로 인한 플래닝 실패/타임아웃 비율 증가(cuRobo 이슈 #595에서 반복 보고) — 재시도 로직과 여유 컴퓨트 필요.
5. 양팔 데이터가 기존 253개 단일팔 데이터 비중을 밀어내지 않도록 혼합비 관리 필요 — 구체적 최적 비율은 문헌에 없음(가설, 실험으로 결정해야 함. "근거 기반 방법론" 규칙대로 테스트로만 채택).
6. 성공 판정은 비전 판정 사례가 문헌에 없으므로 기존 특권(ground-truth) 판정 인프라를 그대로 확장 — 새 비전 판정기를 만들지 않는 게 근거 있는 선택.

## (e) 로봇별 적합도

- **Franka(단일팔)**: 양팔 협응 과제 대상 아님(원천적으로 제외, 기존 단일팔 풀 유지).
- **AI Worker(양팔)**: A~F 전 범주 적합. 기본 레퍼런스 임베디먼트로 권장.
- **Galaxea R1 Pro(양팔, 모바일 휴머노이드형)**: A~F 전 범주 적합. BEHAVIOR-1K 2025 챌린지가 실제로 R1 Pro로 양팔 과제(≈50 tasks, ~10K teleop episodes)를 수집한 선례가 있어 특히 B(양손 들기)·F(정렬/적재) 같은 큰 리치/높이가 필요한 과제에 강점.
- **Unitree G1(양팔+Dex3-1 손)**: A(소형 물체 핸드오버)·C(정밀 고정)·E(재파지)·F(정밀 정렬/삽입)에 적합(손가락 자유도로 정밀 파지 유리). B(쟁반/냄비/대형박스 양손 들기)는 페이로드 한계로 **경량 변형(쟁반·바구니 빈 상태)만 권장**, 중량물(가득 찬 냄비·대형 박스)은 1차 구현에서 제외 또는 검증 후 포함.

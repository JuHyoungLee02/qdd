# v3 조사 14: M2·M3·M5 "2026-09 기준으로 우리 선택이 정말 최고인가"

- 작성: 2026-09-24, v3 조사 에이전트(주제 14)
- 대상: `docs/plan.md` v3.5의 M2(Astra → Jev 전달), M3(촘촘한 객관식 행동), M5(스무딩)
- 결론 세 줄
  - **M2**: 현재 스키마(객체 ID + 완료 술어 + 예상 시간 + 스킬)는 유지. 새 근거 두 개가 방향을 바꾼다. (1) 작은 실행기에는 **"어떻게"(절차)보다 "무엇을"(목표)** 을 주는 쪽이 나았다(COPE, TMLR 2026). (2) 느린 계획기를 기다리지 말고 **빠른 실행기가 계획기의 최신 출력을 참조하며 계속 결정**하는 구조가 시간 압박에서 가장 강했다(AgileThinker, ICLR 2026). 단 Astra는 추론 과정을 공개하지 않으므로 "최종 출력만 참조"하는 축소판만 옮길 수 있다.
  - **M3**: 사용자 방향("촘촘하게")에 대한 **반대 증거가 가장 강한 모듈**이다. 학습 안 한 VLM에게 "방향·크기를 텍스트로 고르게" 하면 약했고(SPF: 텍스트 행동 7% 대 목표 지점 지정 100%), 후보 중에서 고르는 PIVOT식도 40%였다. 반복 미세 이동은 학습 없이는 일반화되지 않았다(GUI-Cursor). → Jev에게 **"어디로(목표 객체·목표 영역)"를 고르게 하고, 크기·경로는 코드가 계산**하는 쪽을 1순위 후보로 올리고, 촘촘한 크기 객관식은 비교 조건으로 둔다. [결정 필요]
  - **M5**: LiPo식 후처리를 **수치로 이기는 비학습 후처리는 찾지 못했다.** 대신 "겹침 구간을 평균하는 후처리는 정밀 작업 성공률을 깎는다"는 반대 증거가 두 곳에서 나왔다(SEAM 표: ACT 시간 앙상블 94.8 → 82.7%, WAM 실물 연구: 끼우기 과제 blend 37.5점). → 스무딩은 **결정 단계(M4 히스테리시스·고정 구간)에서 먼저**, 마지막 층은 **속도·가속·저크 한계를 거는 온라인 궤적 생성(Ruckig)** 또는 LiPo식 QP. 둘 사이 승자는 근거 없음 → 비교 실험.

## 3) 새로 찾은 것과 모듈별 최고 후보

### M2. Astra → Jev 전달

**질문: 큰 모델이 작은·빠른 실행기에게 무엇을 어떤 형식으로 넘길 때 실행기가 실제로 좋아졌나?**

1. **목표(무엇) > 절차(어떻게)** — COPE(TMLR 2026, HIGH)
   - 어디서: MATH-500, Llama-1B. 절차 지침 23.2%(무계획 25.2%보다 나쁨) 대 목표 30.2%. 조건: 1B 자기 계획. 큰 계획기(GPT-4o-mini) → 3B 실행기는 42.8 → 53.0%.
   - 가져올 것: Jev에게 넘기는 것의 중심은 "완료 조건 술어(무엇이 참이 되어야 하나)"이고, 절차 서술은 짧게 또는 스킬 이름으로만.
   - 접목: 현재 M2 스키마의 "완료 조건 술어 + 연결할 스킬"이 이미 이 방향이다. **추가 제안**: Astra가 쓰는 자유 서술 "how" 문단을 Jev 입력에서 빼는 조건을 비교 실험에 넣는다(Jev는 관련 없는 내용에 약하다는 공식 약점과도 맞다).
   - 반대 증거: 같은 논문에서 "큰 계획만으로는 부족"(Plan-only 56.8% 대 전체 COPE 74.4%) — 계획 전달만으로 끝나지 않고 확신 낮을 때 올려 보내는 캐스케이드가 필요. 우리 구조의 "Jev 확신 낮으면 Astra"(M8)와 같다.
   - 큰 모델 → 작은 모델 방향만 도움이 된다(작은 계획기는 큰 실행기를 망친다). Astra → Jev 방향은 맞다.

2. **느린 계획기를 기다리지 않는 병렬 구조** — AgileThinker(ICLR 2026, HIGH, 로봇 미적용)
   - 어디서: Real-Time Reasoning Gym(Freeway, Snake, Overcooked). 환경이 사고 시간과 무관하게 흘러가는 설정. 인지 부하가 올라갈 때 0.88 → 0.50 대 반응 전용 0.89 → 0.15.
   - 가져올 것: 반응 스레드는 매 스텝 "최신 관측 + 계획 스레드의 현재까지 출력"으로 결정. 계획 스레드는 얼어붙은 상태 사본에 대해 계속 생각.
   - Astra 제약: Astra는 추론 과정을 볼 수 없다(OpenAI 추론 모델 공통). 저자도 Gemini에서 **"최종 출력만 참조" 축소판**을 썼고 여전히 개선됐다 → 우리가 옮길 수 있는 것은 이 축소판. 즉 Astra 응답이 도착하면 그때부터 Jev 입력의 "계획" 칸이 바뀌고, 도착 전에는 이전 계획으로 계속 간다. 이는 사용자 방향("처음 이후엔 웬만하면 멈추지 않는다")과 같다.
   - 새로 넣을 것: 계획이 **어느 시점의 상태를 보고 만든 것인지**(상태 시각·프레임 번호)를 계획에 붙인다. WAM 연구가 로봇 쪽에서 "시간 정렬이 최우선"이라고 한 것과 같은 이유.

3. **typed 인터페이스가 계획-실행 분리를 가능하게 한다** — 2605.14290(MED-LOW), Anthropic 블로그(MED), MAST(기간 밖)
   - WebArena 80%가 실행 중 LLM 없이 계획만으로 가능. 조건은 "도구가 효과를 미리 아는 의미 행동"이어야 한다는 것.
   - 우리에게 뜻하는 것: Astra가 넘기는 계획 단계가 **스킬 이름 + 사전조건 술어 + 사후조건(완료) 술어**로 되어 있으면, 매 단계 Jev가 할 일이 "지금 어느 단계인가 / 사후조건이 성립했나 / 다음 보기 중 무엇인가"라는 typed 질문으로 줄어든다.
   - Anthropic의 지시 네 요소(목표, 출력 형식, 도구, 경계)는 M2 스키마 점검표로 쓴다. 우리 스키마에서 "경계"(하면 안 되는 것, 범위 밖)는 아직 없다 → **금지 술어 칸** 추가 제안.
   - MAST의 "종료 조건 모름" 실패 유형 → 완료 술어는 필수 칸.

4. **분기 표기** — Routine(LOW-MED, 참고만)
   - "Step X / Branch X-n Step i: If <조건>, <행동>, using <도구>" 형식. 실행기가 자기 위치를 추적하기 쉽다는 주장. 수치는 한 기업 시나리오라 근거로 쓰지 않는다. 형식만 참고: 우리 계획 단계에 **단계 ID와 분기 ID**를 붙이면 M9 "체크포인트 k 재개" 보기와 그대로 연결된다.

5. GUI 에이전트의 계획기–그라운더 분리(GTA1, Agent S 계열, CoAct-1)
   - 큰 계획기(o3 등)가 자연어로 "무엇을 클릭할지"를 말하고 작은 그라운더(7B)가 좌표를 낸다. OSWorld 상위가 거의 이 구조다(GTA1 45.2%, 2510.02250 72.6%는 다중 롤아웃 선택 포함). 초록 수준만 확인.
   - 가져올 것: 전달 단위가 "요소 설명" = 우리의 **객체 ID 참조**와 같은 자리. M1/M2의 텍스트판 Set-of-Mark 선택을 지지한다. 새로운 형식은 없다.

**M2 결론**: 현재 스키마 유지 + 세 가지 보강 [제안]: (a) 절차 서술 최소화, 목표·완료 술어 중심, (b) 계획에 "기준 상태 시각" 붙이기, (c) 금지 술어(경계) 칸. 형식(JSON 대 YAML)보다 내용이라는 v3/04 결론과 충돌하지 않는다.

### M3. 행동 표현 (촘촘한 객관식)

**질문: LLM/VLM이 이산 선택으로 연속 시스템을 빠르게 제어할 때 무엇이 잘 됐나?**

1. **"어디로"를 고르게 하고 크기는 코드가** — SPF(CoRL 2025, HIGH)
   - 어디서: 드론 항법, 학습 없음. 이미지 위 목표 2D 점 지정 100% / 텍스트 행동 7% / 후보 점 선택(PIVOT) 40%(절제, 항법 과제).
   - Jev는 텍스트만 받으므로 "이미지 위 점 찍기"는 못 한다. 옮길 수 있는 부분은 **목표를 가리키게 하는 것**: 보기 = 객체 ID, 객체의 부분(손잡이, 윗면), 코드가 만든 이름 있는 영역(예: "컵 왼쪽 5cm 지점"). 경로·보폭·자세는 코드가 계산.
   - 깊이/거리는 SPF도 **이산 단계(d∈{1..L}) → 비선형 보폭 곡선**으로 썼다. 즉 "크기"를 고르게 하더라도 거친 몇 단계면 됐다.
   - **plan.md M3의 "PIVOT의 텍스트판"(코드가 후보를 만들고 Jev가 고름)에 대한 반대 증거**: SPF에서 후보 선택형이 직접 지정보다 크게 낮았다. 다만 SPF의 PIVOT은 이미지 위 점 후보이고, 우리 보기는 "예상 결과 술어가 붙은 후보"라 같은 방법은 아니다. 비교 조건으로 유지.

2. **보기는 적고 의미가 분명하게, 크기는 상황에 맞춰 코드가** — Show-Harness(MED, 이미 선점 대상)
   - 방향 6 + 회전 + 그리퍼 정도의 보기, 크기는 2/4cm 두 단계를 코드가 자동 선택. 오류는 세밀한 잡기·놓기에 몰림(v3/06).
   - 우리 계획의 "차원당 ≤255 보기"는 이보다 100배 이상 촘촘하다. 촘촘한 보기가 거친 보기를 이긴다는 **학습 안 한 LLM의 근거는 찾지 못했다.** VLA-0의 "250 대 1000 차이 1.5점"은 미세조정 모델 결과다.

3. **반복 미세 이동은 학습 없이 일반화되지 않는다** — GUI-Cursor(ICML 2026, HIGH)
   - 학습 안 한 GPT-4o: 10스텝 이동으로 조금 오름(17.5 → 25.5%). GUI 학습된 7B는 반복 이동에서 붕괴(88.8 → 1.3%). 저자: 미세조정이 필요.
   - 뜻: "Jev가 1초에 여러 번 작은 증분을 고른다"는 M3/M4 설계는, 한 번 좌표를 맞히는 능력과 다르다. **학습할 수 없는 Jev에게는 증분 제어가 약점일 수 있다.** 우리 첫 실험에서 반드시 "증분 보기" 대 "목표 지정 보기"를 비교한다.
   - 같은 논문의 학습 없는 거친→세밀 자르기(CCF)는 ScreenSpot-Pro에서 이득이 있었다(GTA1에 적용 시 GUI-Spotlight보다 +2.2%p) → plan.md의 "2단계 줌" 비교 변수를 지지한다.

4. **보기 = 부드러운 운동 원형** — AutoVLA(NeurIPS 2025, HIGH, 학습형)
   - 텍스트 좌표보다 궤적 조각 코드북(2,048개)이 PDMS 71.31 → 80.54, 실행 시간도 절반.
   - Jev는 이름 없는 2,048 토큰을 배울 수 없다. 옮길 수 있는 것: **보기 하나 = 이름 붙은 짧은 궤적 원형**(예: "접근-직선", "접근-위에서 내려옴", "옆으로 비켜 접근"). 원형은 미리 부드럽게 만든 것이라 M5 부담이 준다. BEAST 제어점(plan.md)과 같은 방향.

5. 실시간 게임 — AgileThinker(ICLR 2026)
   - 반응 스레드는 보통 몇 개의 이산 행동(Freeway: 위/아래/정지)을 매 스텝 고른다. 보기 수가 적어도, 계획 스레드 정보를 참조하면 부하가 큰 상황에서 버텼다. "보기를 촘촘히"보다 "좋은 계획 문맥"이 효과가 컸다는 간접 근거.

6. 정답 없는 보기 문제 — "Wait, that's not an option"(ACL 2025, HIGH)
   - 맞는 보기가 없어도 모델은 하나를 고른다. → 모든 Jev 행동 질문에 **"해당 없음 / 멈추고 올림"** 보기를 넣는다(M8 호출 트리거로 연결).

**Show-Harness와 비교 (차별점 정리)**

| 축 | Show-Harness | 우리 현재안(plan.md M3) | 이번 조사 후 제안 |
|---|---|---|---|
| 결정 모델 | 최상위 VLM(이미지 입력), 또는 미세조정 2B | Jev(텍스트만, 학습 불가) | 같음 |
| 보기 | 축 방향·회전·그리퍼, 크기 고정(2/4cm) | 차원당 ≤255 순서형 보기 | **목표 지정 보기(객체·부분·영역 ID) 1순위**, 증분 방향 보기 2순위, 촘촘한 크기 보기는 비교 조건 |
| 크기 | 코드 규칙(손목 가시성) | Jev 최빈 구간 | 코드(거리 기반 적응 보폭, SPF·Show-Harness 공통) |
| 호출 빈도 | 스텝마다, 멀면 여러 단위 묶음 | 1초 여러 번 계단식(M4) | 같음(M4) |
| 확률 사용 | 없음 | Jev 확률로 게이트·합의 | 같음(차별점) |

**M3 결론** [제안]: "촘촘한 객관식"의 **촘촘함을 크기 해상도가 아니라 결정 빈도와 목표 지정 해상도(어느 객체의 어느 부분)** 에 두는 쪽이 근거가 더 많다. 사용자 방향과 어긋날 수 있으므로 [결정 필요]로 둔다. 실험 조건: (A) 목표 지정 보기 + 코드 보폭, (B) Show-Harness식 방향 + 거친 크기 2~3단계, (C) 현재안 촘촘한 크기(≤255), (D) 이름 붙은 궤적 원형.

### M5. 스무딩

**질문: 이산 결정이 흔들리는 제어기에 쓸 비학습 스무딩 중 무엇이 가장 근거가 있나? LiPo를 이기는 것이 있나?**

1. **반대 증거: 겹침 평균은 정밀도를 깎는다**
   - SEAM 비교표(LIBERO-10, π0.5, 과제당 130회): ACT 시간 앙상블이 가장 부드럽지만(경계 저크 0.195 → 0.031) 성공률 94.8 → 82.7%.
   - WAM 실물 연구(5회씩): 사후 블렌딩은 끼우기 과제에서 37.5점으로 블렌딩 없는 것(40)과 다르지 않았다. 저자 결론 "블렌딩은 최저선, 정밀 과제에서 정확도 희생".
   - 원인(두 논문 공통 서술): 서로 다른 모드(예: 왼쪽으로 돌기 대 오른쪽으로 돌기)를 평균하면 둘 다 아닌 동작이 된다. **이산 선택기(Jev)는 이 문제가 더 심하다**(보기 사이 뒤집힘이 바로 모드 전환이다).
   - → LiPo의 "겹침 선형 블렌딩"은 **같은 보기(같은 모드)끼리 이어질 때만** 쓰고, 보기가 바뀐 경계에서는 쓰지 않는다.

2. **1층: 결정 단계에서 막는다 (M4와 공유)**
   - RTC식 고정 구간 + 히스테리시스(plan.md M4)가 사실상 가장 강한 "스무딩"이다. SEAM·WAM 모두 "다음 결정을 이전 계획과 일관되게 만드는 방법(RTC, 접두 조건화)"이 사후 평균보다 정밀도를 지켰다. 학습형(train)은 Jev에 못 쓰므로 추론 시점 판(고정 구간 + 이전 선택 유지 규칙)만 가져온다.
   - WAM 연구의 첫 교훈 "관측·예측·실행 시간 정렬"은 Jev에도 그대로: **각 Jev 결정이 어느 시각의 상태를 보고 낸 것인지 기록하고, 실행기는 그 시각 기준으로 겹침을 맞춘다.** 정렬이 틀리면 어떤 스무딩도 못 고친다.

3. **2층(마지막): 한계 걸린 궤적 생성**
   - 후보 A: **Ruckig 저크 한계 온라인 궤적 생성**(RSS 2021, 기간 밖 기초 문헌). FluxVLA(2026-09, MED)가 VLA 배치의 표준 층으로 채택, 1.17ms/12자유도. 새 목표가 오면 현재 속도·가속을 유지한 채 목표로 이어지므로 **이산 목표 점프를 자연히 흡수**한다. 과제 성공률 근거는 없음(저자 명시).
   - 후보 B: 관절 분리 MPC 추적(FluxVLA의 다른 백엔드, 4.90ms). 추적 정밀도가 더 좋고 지연이 더 크다.
   - 후보 C: LiPo식 제한 섭동 저크 최소화 QP(현재안). 근거는 한 로봇 동적 과제.
   - 후보 D: 저역 통과(REAL-I 공식 파이프라인), one-euro(CHI 2012, 기간 밖 기초 문헌, 속도에 따라 차단 주파수를 바꿔 정지 시 떨림과 이동 시 지연을 함께 줄임). 로봇 과제 비교 근거는 찾지 못했다.
   - **A~D 중 과제 성공률로 서로 비교한 연구는 없다.** "LiPo를 이긴다"고 말할 근거는 없다. 다만 Ruckig은 (1) 더 단순하고 (2) 하드 한계를 보장하고 (3) 2026년 공개 배치 스택에서 쓰인다는 점에서 **기본값 후보로 LiPo와 동등 이상**이다.

4. 결정 모양 자체로 줄이기(M3와 연결)
   - 보기를 "이름 붙은 궤적 원형"(AutoVLA의 발상)이나 목표 지정(SPF)으로 바꾸면, 결정이 바뀌어도 코드가 만드는 경로는 이미 부드럽다. 스무딩 층에 걸리는 부담 자체가 준다.
   - Show-Harness·SPF의 거리 기반 적응 보폭도 떨림을 줄이는 쪽이다(목표 근처에서 작은 보폭).

5. LLM 분야에서 새 스무딩 방법: 이번에도 찾지 못했다. 가장 가까운 것은 AgileThinker의 "반응 스레드가 계획의 최신 출력에 조건화" = 결정 일관성 쪽이다(검색어: real-time reasoning agents, dual thread, streaming LLM control).

**M5 결론** [제안]: 3층 구조. (1) 결정 단계: M4 고정 구간 + 히스테리시스 + 시간 정렬 기록, (2) 같은 보기끼리만 겹침 블렌딩, 보기가 바뀌면 블렌딩 없이 새 목표, (3) 마지막 층 Ruckig(기본) 대 LiPo QP 대 MPC 비교. 기준 방법에 "시간 앙상블(전체 평균)"을 넣어 SEAM·WAM에서 본 정밀도 하락이 우리 설정에서도 나오는지 확인.

## 4) 반대 증거와 위험

- **사용자 방향 "행동 표현은 촘촘하게"에 대한 반대 증거** (README 규칙 7): SPF(텍스트 행동 7%), GUI-Cursor(학습 없는 반복 미세 이동 붕괴), Show-Harness(거친 보기로 결과). 단 세 논문 모두 VLM + 이미지 입력이고 Jev(텍스트, 확률 출력)와 다르다. Jev에서 재현될지는 모른다.
- 반대로 촘촘함을 지지하는 약한 근거: 거친→세밀 2단계(CCF, 학습 없이 이득). 크기 해상도보다는 "단계적 좁히기"를 지지한다.
- M2의 COPE 근거는 수학 문제(MATH-500)와 1~3B 모델이다. Jev의 크기·능력은 공개되지 않았다. "목표 > 절차"가 Jev에서도 성립하는지는 측정해야 한다.
- AgileThinker의 부분 추론 공유는 Astra에서 불가능하다. 축소판(최종 출력만) 효과의 수치는 읽지 못했다.
- M5의 실물 근거(WAM)는 조건당 5회뿐이다. SEAM은 130회지만 시뮬레이션이고 소속 미확인.
- Ruckig·MPC는 FluxVLA에서 **과제 효과 미측정**. 채택 사례일 뿐 성능 근거가 아니다.
- 계약/사전·사후조건 논문들은 대부분 LOW(단일 저자, 특허 표기, 투고 중). "계약 형식이 실행기를 좋게 한다"를 HIGH 근거로 말할 수 없다.

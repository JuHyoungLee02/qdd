# VLM이 "로봇 기준 좌우"를 스스로 알아채게 하는 법 — 문헌 조사와 권장안 (2026-10-02)

작성 2026-10-02, 문헌 조사 전용. GPU·유료 API 호출 0원. 학습·평가는 하지 않았다. 조사는 arXiv API(export.arxiv.org)와 GitHub 저장소 API로 직접 확인했다(WebSearch 예산이 세션 전체에서 소진되어 사용 불가 — 그래서 arXiv/GitHub API를 bash로 직접 질의했다). 별·날짜는 모두 2026-10-02 기준.

## 0. 문제 정의 (재확인)

- 조종 VLM(Qwen3.5-35B LoRA)이 머리 카메라 영상을 보고 픽셀 점 + 접근 방향을 낸다.
- 지시문의 방향 단어("병 왼쪽에 놓아", "책 앞-오른쪽")는 **로봇 자신의 몸 기준**으로 정의된다.
- 일부 학습 영상은 3인칭이라 로봇을 마주 보면 영상의 왼쪽이 로봇의 오른쪽이 된다. 머리 카메라도 높이·피치·화각이 랜덤으로 기울어진다.
- 목표: VLM이 "이 영상은 어느 쪽에서 찍혔나"를 **스스로** 알아채서 좌우 반전에 혼동되지 않게 한다. 카메라 자세를 글로 알려주는 줄은 선택 사항(줄 수도 있다).
- 규칙(사용자 메모리 `feedback_no_lower_reasoning_effort`, `feedback_natural_diverse_grasp` 등과 같은 결): **VLM을 절대 혼동시키지 않는다** — 규칙 하나, 모순 라벨 없음.

## 1. 근거 강도 표기

- **강**: 학회/저명 벤치마크 논문 + 독립 근거 2개 이상, 또는 여러 연구가 같은 결론.
- **중**: 프리프린트 1편이되 결과가 구체적(수치로 실패 양상 제시), 또는 별 ≥ 300 저장소.
- **약**: 프리프린트 1편, 결과가 정성적이거나 저장소가 작음(별 < 50) 또는 비공개.
- **[기초]**: 2024-04 이전 공개 — 1.5년 규칙 밖. 배경 지식으로만 인용.
- **가설**: 문헌으로 직접 확인 못함. 이 문서에서는 "건너뛸 때" 명시한다.

## 3. 문헌이 말해주는 것 (종합)

1. **자기중심 편향은 반복 재현된 사실이다** (강). FlipSet: 모델 대부분이 Level-2 시점 전환에서 '찍은 카메라의 시점'을 정답으로 내놓는다(오류의 ~75%). "Seeing Through Their Eyes"도 2024년에 같은 결론. → 우리가 걱정하는 "영상-왼쪽 vs 로봇-오른쪽 혼동"은 VLM 전반의 기본 실패 양상이며, 추가 보정 없이는 Qwen3.5도 같은 함정에 빠질 것으로 봐야 한다.
2. **학습 가능한 해법 두 갈래가 있다**:
   - (a) **진단/주석 중심** — ViewSpatial-Bench, SAT, VQASynth, Spatial457 모두 "3D GT(또는 시뮬레이터)에서 방향·관계 라벨을 자동 생성"하는 파이프라인을 쓴다. 렌더를 다시 하지 않고 기존 이미지에 새 QA 텍스트만 붙인다 — 우리 빌드 파이프라인과 바로 호환.
   - (b) **명시적 기준좌표계 학습** — LeRF(VLM), CamVLA(로봇정책)는 "모델이 스스로 기준좌표계/카메라-로봇 관계를 예측하는 보조 출력"을 두고 SFT(+RL)로 가르친다. 둘 다 "글로 알려주지 말고 추론하게 하라"는 철학이 최근(2026) 추세로 자리잡고 있다(중).
3. **합성적 결함(compositional deficit)**이 FlipSet에서 확인됐다(강): 공간 변환(심적 회전)과 사회적 관점취득을 각각 테스트하면 되는데, 결합하면 깨진다. → 보조 과제를 "점 찍기"와 "관점 전환"을 분리해서만 테스트하면 과대평가될 위험이 있다. 결합형 과제가 필요하다.
4. **거울반전 증강(mirror/flip augmentation)**은 특정 논문으로 못 박기보다 로봇학습 커뮤니티의 일반 관행(RT류·OpenVLA 계열 이미지 증강에서 흔함)이다 — 이 문서에서는 **[가설/관행]**으로 표시하고, 이미지·깊이·점·텍스트를 전부 같은 변환으로 묶어야 한다는 원칙만 차용한다.

## 4. 권장안

### (1) 방향 단어 고정 규약
- **모든 방향 단어는 로봇 베이스 프레임(로봇이 보는 "앞") 기준으로만 정의한다.** 카메라 프레임, 뷰어(사람) 프레임 기준은 절대 쓰지 않는다 — 이것이 FlipSet이 밝힌 실패 양상(카메라 시점으로 default)을 원천에서 막는 단 하나의 규약이다.
- 좌표 변환은 전부 **빌드 코드**에서 한다(시뮬 GT 로봇 자세 + 카메라 외부 파라미터는 둘 다 안다). VLM에게는 "이미 로봇 기준으로 변환된" 텍스트 라벨만 준다 — 라벨 생성 단계에서 모순이 생길 수 없게 설계.
- 카메라 자세 텍스트 줄은 **써도 되지만 정답을 대신하면 안 된다** — CamVLA의 교훈("정답을 알려주지 말고 추론하게")을 따라, 카메라 자세 줄이 있어도 방향 라벨은 항상 VLM의 추론 결과와 비교해 보조손실로 체크한다(아래 (2) 참고). 즉 카메라 줄은 힌트로 주되, 그것 없이도 맞혀야 하는 과제를 반드시 섞는다.

### (2) 빌드 타임 보조 학습 행 (재렌더 없이 시뮬 GT에서 생성)
ViewSpatial-Bench/SAT/VQASynth 방식을 그대로 가져온다 — 이미지는 그대로 두고 텍스트 라벨만 기존 빌드 메타데이터(물체 3D 위치, 로봇 베이스 자세, 카메라 외부 파라미터 — 전부 이미 시뮬에 있음)에서 뽑는다.

1. **관점 QA**: "로봇의 시점에서, A는 B의 왼쪽/오른쪽/앞/뒤에 있는가?" — 두 물체의 3D 위치를 로봇 베이스 프레임으로 좌표변환 후 부호만 보면 정답이 나온다. 같은 이미지에 카메라가 로봇을 마주 보는 경우(3인칭)와 뒤에서 보는 경우(머리캠)를 섞어서, **같은 기하가 다른 화면배치로 나타나는 쌍**을 의도적으로 만든다.
2. **"로봇 자신의 왼쪽/오른쪽을 짚어라"**: 로봇 베이스 좌표계에서 "왼쪽 방향의 한 점"(예: 베이스 원점 + 로봇-왼쪽 단위벡터 × 임의 거리)을 정의하고, 그 3D 점을 현재 카메라의 내·외부 파라미터로 픽셀에 투영한다 — 이것도 재렌더 없이 기존 프레임 메타데이터만으로 라벨 생성 가능. 3인칭·기울어진 머리캠 모두에서 "다른 픽셀, 같은 의미"를 반복적으로 보여주는 것이 FlipSet이 지적한 합성적 결함(결합 과제 부족)을 직접 다루는 길이다.
3. **카메라-상대 요(yaw) 추정 보조과제**: 카메라 전방벡터와 로봇 전방벡터 사이 각도를(시뮬 GT로 정확히 안다) 성기게 구간화(예: 정면/측면/후면 3~5급) 해 분류 라벨로 쓴다. LeRF의 "명시적 기준좌표계 예측" 보조출력, CamVLA의 "핸드-아이 행렬 예측"과 같은 자리다 — 다만 우리는 라벨이 시뮬 GT에서 공짜로 나오므로 학습을 가볍게 시작할 수 있다.
4. **거울반전 증강은 2차 과제로만**: 카메라가 로봇을 거의 정면으로 마주 보는 프레임에서만, 이미지+점+방향텍스트를 한 변환으로 동시에 뒤집어 데이터를 2배로 늘릴 수 있다(관행, 근거 **가설**). 깊이값·픽셀점·좌우 텍스트가 하나라도 따로 뒤집히면 바로 모순 라벨이 생기므로, 빌드 파이프라인에서 원자적으로(하나의 변환 함수로) 처리해야 한다 — "모순 라벨 없음" 규칙과 직결.

### (3) 테스트 프로토콜
- **8B 체크암**: 본 35B LoRA와 분리된 작은 8B를 같은 레시피로 미세조정해 "이 보조행들이 실제로 통하는지"를 저비용으로 먼저 본다(기존 E-VIEW8 체계와 같은 틀, `docs/stage3/results/view8.md` 참고).
- **평가 서브셋**: 빌드 메타데이터(카메라 종류=3인칭/머리캠, 카메라-로봇 상대 요 구간, 방향 단어 종류)로 **자동 계층화**한 held-out 세트를 만든다 — ViewSpatial-Bench의 보고 포맷을 따라 "자기중심(머리캠 정면)" vs "타자중심(3인칭/기울어진 머리캠)" 정확도를 나눠서 report.
- **통과 기준**: 3인칭·기울어진 카메라 세트의 방향단어 정확도가 머리캠 정면 세트보다 **크게(통계적으로) 낮지 않아야** 한다. FlipSet의 결합과제 교훈에 따라, "점 찍기 단독"과 "관점 QA 단독"이 아니라 **점 찍기+관점이 결합된 지시문**으로 반드시 테스트한다.
- 기존 체계(E-VIEW8, A/A 마진)와 같은 틀로 수 mm/수 px 단위 잡음을 감안해 판정한다 — `docs/research/generalist_crossview_2026-10-01.md` §0.1-3,4 참고.

### (4) 위험
- **가장 큰 위험(강 근거)**: 자기중심 편향은 VLM의 기본 실패 모드다(FlipSet 75%, Seeing Through Their Eyes). 아무 대책 없이 3인칭·기울어진 카메라를 섞으면 모델이 "화면의 왼쪽"을 "로봇의 왼쪽"으로 잘못 고정할 확률이 높다.
- **"VLM을 혼동시키지 않는다" 규칙 위반 경로**: 카메라 자세 텍스트 줄과 실제 방향 라벨이 **단 하나의 빌드 버그로도** 어긋나면 바로 모순 라벨이 생긴다 — 좌표변환·투영을 전부 한 함수에 모아 단위테스트(기존 물체 위치 몇 개로 손-계산 대조)를 두는 게 싼 안전장치다.
- **합성적 결함 위험**: 점찍기와 관점추론을 따로만 학습/평가하면 벤치마크 점수는 좋아도 실제 결합 상황(지시문이 동시에 "왼쪽"+"가까이 짚기"를 요구)에서는 깨질 수 있다(FlipSet 교훈) — 반드시 결합형 보조행·결합형 평가를 포함해야 한다.
- **거울반전 증강 risk**: 근거가 특정 논문이 아니라 관행 수준(가설)이라, 과신하지 말 것. 깊이·그리퍼 자세처럼 "물리적으로 비대칭인" 필드(예: 로봇 팔이 원래 오른팔만 있는 경우)에는 통째로 적용 금지 — 좌우 대칭이 성립하는 필드에만 한정.
- **카메라 자세 텍스트 줄의 함정**: 줄을 늘 정확하게 주면 VLM이 "글을 읽고 답을 베끼는" 지름길을 배워 스스로 추론하는 능력을 안 기를 수 있다(이것이 바로 CamVLA 논문이 "알려주지 말고 추론하게"를 주장하는 이유). 줄을 주더라도 일부 학습 샘플에서는 빼거나 일부러 덜 정확하게 주는 식으로 "줄만 믿지 못하게" 만드는 설계가 필요하다 — 단, 이것도 사용자 승인 필요한 설계 결정이라 **제안만** 해둔다.

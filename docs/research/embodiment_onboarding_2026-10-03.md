# 새 로봇을 "VLA처럼" 자연스럽게 추가하기 — 기체 온보딩 도구 + 적응 프로토콜 조사 (2026-10-03)

작성 2026-10-03, 문헌·도구 조사 에이전트. 학습·GPU·파드 실행 0건, 유료 호출 0원. 질문·기존 코드 읽기 + arXiv/GitHub 패치만 확인.

- 배경: Fly-by-Wire 상위 VLM(Qwen3.5-35B-A3B LoRA)은 매 호출마다 **로봇 불문(agnostic) 명령만** 낸다 — 영상 점 + 높이, 접근 방식 + 15° 손목 회전 빈, 팔 좌/우, 그리퍼 의도, 스킬, 관절물체 point2/axis. 입력은 고정 4캠(head·wrist_left·wrist_right·third_person) + `robot:` 줄 + `camera:` 줄. 기체별 실행(cuRobo 설정·TCP·그리퍼 폭표·reach map·ready pose)은 전부 코드에 있다. L9 데이터는 AI Worker(양팔)·Franka·Galaxea R1 Pro(양팔)·Unitree G1(Dex3-1 3지 핸드) 4종.
- 사용자 목표: "어떤 로봇이 들어와도 VLA처럼 추가 학습만으로 자연스럽게 추가"할 수 있게 (A) URDF+손 사양 → cuRobo 설정·TCP·그리퍼 폭표·reach map·ready pose·렌더 점검을 자동 생성·자가검증하는 온보딩 도구, (B) leave-one-robot-out 영샷 → 50·200편 few-shot 미세조정 적응 프로토콜.
- **하드 제약(사용자 원문 취지): 방법론이 과도하게 복잡해지면 안 된다. 근거가 있는 가장 단순한 방법을 우선한다.**
- 규칙: 1.5년(2025-04 이후) 또는 별 많은 GitHub. 날짜·별·라이선스는 2026-10-03 GitHub/arXiv 실측(WebFetch, API 검색 예산 소진으로 검색 대신 직접 패치 확인). 확인 못 한 수치는 표시한다. 근거 강도: **강** = 공개 코드·수치로 직접 확인 / **중** = 논문 주장(원문 인용)이나 README 설명뿐, 교차 검증 못함 / **약** = 페이지 접근 실패·기억 기반, 별도 표시.

## 0. 결론 요약

1. **거의 모든 성공한 cross-embodiment VLA는 "행동 벡터를 로봇에 맞춰 자르거나 채우는" 가장 단순한 방법을 쓴다.** 공통 차원의 "통일 행동 벡터"에 각 로봇의 실제 축을 꽂아 넣고(RDT-1B), 남는 슬롯은 0으로 채우거나 마스킹한다(π0/π0.5, GR00T). 복잡한 학습형 임베딩 공간(UniAct)도 있지만 공개 증거는 적다(245★, 논문 교차검증 못함). **우리 설계(상위는 영상 점+높이라는 로봇 불문 공간, 하위 실행만 로봇별 코드)는 이미 이 원칙과 같은 방향이다** — 오히려 더 단순하다: 상위는 숫자 행동 벡터조차 만들지 않는다.
2. **새 로봇 적응에 드는 데이터는 문헌에서 일관되게 "작다": 수십~수천 에피소드, 때로 5~50편.** Octo README는 "small target domain dataset"만 요구한다고 명시(강, GitHub 확인). GR00T 데모셋은 5편짜리로 미세조정 예시가 있다(강, GitHub 확인, 다만 "작아도 된다"는 보장이 아니라 예시임에 주의). RDT-1B 자체 수집 미세조정은 6천여 편(강, README). HPT는 frozen trunk + 작은 새 stem/head 조합을 권장(강, GitHub). 즉 **새 기체 전용 데이터는 "VLA 전체를 다시 학습"할 양이 아니라 "새 축 매핑을 배우는" 양**이라는 공통 패턴이 있다. 우리 50/200편 설계는 이 범위 안에 있다.
3. **계층형 점/키포인트 상위 모델(HAMSTER, MolmoAct, RoboPoint, MOKA)은 상위 VLM 자체를 로봇별로 재학습하지 않는다 — 좌표가 이미 영상 픽셀·카메라 좌표계라 로봇과 무관하기 때문.** HAMSTER(중, 공식 페이지 확인·GitHub 별수 미확인)는 하위 정책만 RVT2/3D-DA로 바꿔 끼우고 상위 VLM은 그대로 썼다고 결과표로 보여준다(바꾼 것은 저수준 정책, 상위 경로 생성기는 고정). MolmoAct·RoboPoint도 2D/3D 점 출력이 카메라 내부파라미터(초점거리·주점)만 알면 어떤 로봇에도 투영 가능해 **구조적으로 미세조정이 필요 없다** — 이는 우리 설계(상위가 영상 점+높이만 낸다)가 이미 선택한 길과 동일하다. 단, MolmoAct 자체 README는 "자기 수집 데이터로 과제 특화 미세조정·LoRA를 권장"한다고 적어, 영샷이 완벽하진 않다고 밝힌다(강, GitHub 확인).
4. **URDF→로봇 설정 자동화는 "완전 자동"이 아니라 "반자동 + 반드시 사람/스크립트 눈으로 확인"이 표준이다.** cuRobo 공식 튴토리얼은 URDF→USD 변환 뒤 Isaac Sim의 Lula Robot Description Editor로 충돌구를 "대화형으로" 만들고 복사해 넣는 절차를 명시한다(강, 공식 문서 확인) — 완전 자동 sphere-fitting 알고리즘은 공식 경로에 없다. 검증은 `motion_gen_reacher.py --visualize_spheres`로 **사람이 본다**(강). 즉 사용자가 요청한 "자동 생성 + 자가 점검" 도구는 **기존 생태계에 없는 조각을 우리가 채워야 한다** — 이는 복잡도를 추가할 핑계가 아니라, 검증 가능한 소형 스크립트 묶음으로 가야 한다는 뜻.
5. **권고(상세 3·4절): 로봇별 상태(proprio) 입력은 기본 추가하지 않는다(NO).** 상위 VLM은 지금처럼 영상+점만 쓰고, 로봇 상태는 하위 코드/JCR에만 흐르게 둔다. 근거: (a) 우리 상위 출력이 이미 로봇 불문 영상 좌표라 proprio가 끼어들 자리가 없다, (b) HAMSTER·MolmoAct·RoboPoint 등 유사 계층 구조에서 상위에 로봇 상태를 넣는다는 공개 근거를 찾지 못했다(없다≠틀렸다, 미확인 표시), (c) 사용자 하드 제약(단순성 우선) — proprio를 넣으면 "새 로봇마다 상태 정규화·패딩·누락축 처리"라는, 이번 조사의 1번 결론이 지적한 복잡도를 상위에 다시 끌어오게 된다. 넣을 이유가 생기면(예: 상위가 짧은 블라인드 구간에서 접촉 여부를 추정해야 하는 경우) JCR 쪽에 한정해서 검토한다.

## 2. 계층형 점/키포인트 시스템의 새-로봇 포팅 (주제 2)

| 시스템 | 근거 | 상위가 내는 것 | 새 로봇 포팅 시 상위 재학습 필요성 |
|---|---|---|---|
| **HAMSTER** | 공식 페이지 확인(중, GitHub 별수·라이선스는 이번 조사에서 미확인 — 페이지 접속 실패[429]). arXiv 2502.05485(2025-02-08) — **[기초], 1.5년 기준 밖**, ICLR 2025 poster | 2D 경로/키포인트(영상 좌표) | **아니오(구조적).** 같은 상위 VLM을 RVT2(66.56%)와 3D-DA(72.55%) 두 하위 정책에 그대로 연결해 성공률을 보고 — 하위만 교체, 상위 고정(중, 결과표 인용) |

| **MOKA** | GitHub moka-manipulation/moka **102★, MIT**(강, 직접 확인) | 마킹 기반 키포인트(Grounded-SAM/GroundingDINO로 분할 후 표시) | 문서상 VLM 자체의 로봇별 미세조정 요구 없음(미확인) — 정책(저수준) 쪽만 Octo로 RLDS 변환해 미세조정하는 경로가 있음, 이는 하위의 일 |

**결론**: 4개 시스템 모두 상위가 다루는 좌표가 **영상/카메라 평면**이라는 공통점 때문에, "로봇이 바뀌어도 상위는 그대로, 하위/실행만 바뀐다"는 구조가 성립한다(HAMSTER가 가장 명시적 증거). MolmoAct만 완전 영샷을 주장하지 않고 LoRA 미세조정을 권고한다 — 이는 우리 상위도 "완전 영샷을 기대하지 말고, 새 로봇마다 가벼운 LoRA 적응 단계를 기본값으로 둔다"는 설계가 문헌과 맞는다는 근거다. **우리 Fly-by-Wire 상위(점+높이+접근방식+회전빈)는 이 네 시스템보다 더 로봇 불문적이다** — 그리퍼 폭·TCP·reach 제약을 아예 상위에 노출하지 않기 때문. 따라서 leave-one-robot-out 영샷 성능이 이들보다 높게 나올 수 있다는 가설은 타당하지만, 검증 전까지는 few-shot(50/200편) 적응 단계를 기본으로 설계해야 한다(MolmoAct 선례).

## 3. 자동 로봇 셋업 도구 조사 (주제 3)

### 3.1 URDF → cuRobo yml + sphere fitting
- 공식 경로(강, curobo.org 튴토리얼 직접 확인): URDF→USD 변환 → **Isaac Sim의 Lula Robot Description Editor로 대화형 충돌구 생성** → yml에 복사. 완전 자동 sphere-fitting 알고리즘은 cuRobo 공식 배포에 없다.
- 검증 경로: `motion_gen_reacher.py --robot <yml> --visualize_spheres`로 **사람이 시각 확인**(강). 즉 "자가 점검"은 공식적으로 "렌더해서 사람이 본다"이고, 수치 self-check(충돌구가 실제 메시를 감싸는지 자동 측정)는 표준 도구에 없다 — 우리가 직접 만들 부분.
- cuRobo 저장소 메타: NVlabs/curobo **1.9k★, Apache-2.0**(강, 직접 확인).

### 3.2 Isaac Lab 로봇 임포트
- 이번 조사에서 Isaac Lab import 공식 문서를 직접 패치하지 못했다(WebSearch 예산 소진, WebFetch 범위 밖) — **[미확인]**. 일반 지식으로는 URDF Importer 확장(usd 변환 + 관절/링크 매핑 UI)이 있으나, 본 문서에서 수치·버전을 주장하지 않는다. 필요 시 별도 짧은 조사로 보강.

### 3.3 그리퍼 폭/간극 보정(충돌 메시 기반)
- 이번 조사에서 "충돌 메시로부터 자동 폭표 생성"을 다루는 1.5년 내 전용 논문/저장소를 특정하지 못했다(**[미확인]**, 검색 예산 소진). 단, 관련 L9 자체 문서(`docs/research/grip_aperture_2026-10-02.md`)가 이미 "접점 폭 + 여유" 방식을 권장하고 있어, 이번 조사의 "슬롯에 꽂기" 원칙(1절)과 일치한다 — **완전 자동 폭표는 문헌 의존 대신 우리가 가진 충돌 메시 + 간단한 스윕(그리퍼를 폭 0→최대까지 움직이며 self-collision 거리 측정)으로 직접 만드는 것이 가장 단순**하다고 판단한다(설계 권고, 4.1절).

### 3.4 역도달가능성 지도(inverse reachability map)
- 이번 조사에서 1.5년 내 전용 신규 논문을 특정 확인하지 못했다(**[미확인]**, 검색 예산 소진). 고전 기법(복셀별 IK 성공률 샘플링, 예: Reuleaux류 — **[기초], 미검증**)은 원리상 단순하고 cuRobo의 배치 IK로 바로 재현 가능하다: 작업공간을 격자로 나누고 각 셀에서 N개 자세에 대해 cuRobo IK 성공률 + 충돌 여부를 세는 것만으로 충분하다(새 알고리즘 불필요 — 단순성 원칙에 부합).

**종합**: 자동화 생태계는 "yml 뼈대 생성은 있음, 충돌구/폭표/reach map의 수치적 자가검증은 표준에 없음"이 현재 상태다. 즉 사용자가 요청한 도구(A)는 **기존 도구를 이어 붙이는 작은 래퍼**로 충분하며, 새로운 알고리즘 연구가 필요하지 않다 — 이것이 단순성 제약과 가장 잘 맞는다.

## 4. 권고

### 4.1 최소 온보딩 체크리스트/도구 설계 (A)
입력: URDF(+메시) 1개, 손/그리퍼 사양(지문: 지점 수·열림 폭 범위·충돌 메시) 1개. 전부 **기존 라이브러리 호출 순서를 고정한 스크립트**로, 새 알고리즘 없음:
1. URDF → USD 변환(cuRobo/Isaac 표준 유틸) → `robot.yml` 뼈대(cuRobo template.yml 기반) 자동 채움(링크명·joint 리밋·acc/jerk는 URDF에서 그대로 추출).
2. **충돌구**: Lula 에디터 대신, 메시 포인트클라우드에 대해 반지름을 이분탐색하며 "구가 메시를 벗어나지 않는 최대 반지름"을 링크마다 자동 계산(간단한 기하 계산, 알고리즘 신규 연구 불필요) → `motion_gen_reacher.py --visualize_spheres` 렌더로 사람 1회 확인(기존 도구 재사용, 3.1).
3. **TCP**: 그리퍼/핸드 사양에서 손끝 중심·접근축을 계산(현재 로봇들과 동일 관례).
4. **그리퍼 폭표**: 충돌 메시로 손가락을 0→최대까지 스윕하며 self-collision 거리로 "실제 벌어지는 폭"을 측정 — 카탈로그 스펙이 아니라 **실측값**(3.3 권고와 동일 원칙).
5. **reach map**: cuRobo 배치 IK로 작업공간 격자의 성공률/충돌 맵 생성(3.4, 신규 알고리즘 없음).
6. **ready pose 탐색**: reach map이 가장 높은 성공률을 보이는 영역 중심에서 자세 후보를 cuRobo IK로 뽑아 자가 충돌·관절한계 점검.
7. **렌더 점검(자가검증)**: 4캠 슬롯(head/wrist_left/wrist_right/third_person) 각각에서 ready pose 렌더 1장 + TCP/그리퍼 폭표 수치를 오버레이해 사람이 1회 눈으로 확인하는 스크립트 — "자동 생성 + 자동 수치 점검 + 사람 최종 확인 1회"가 cuRobo 공식 관행(3.1)과 일치하는 최소 단계다.
- **하지 않을 것**: 학습형 임베딩, 새 시뮬레이터, 메시 자동 리토폴로지, 로봇별 전용 알고리즘 — 전부 문헌에서 증거가 약하거나(UniAct) 표준에 없는 길이라 단순성 제약 위반.

### 4.2 최소 적응 프로토콜 (B)
- **측정**: leave-one-robot-out(4종 중 1종 제외 학습) 영샷 성공률/접근오차 → 그 다음 같은 로봇 50편·200편 few-shot 미세조정 후 재측정. 비교축은 항상 "같은 평가 세트, 같은 지표"(접근 xy 오차 중앙·성공률), 다른 자체 문서들과 동일 관례.
- **데이터 크기**: Octo("small dataset")·GR00T(수천 스텝, 데모 5편 예시)·RDT(6천여 편, 다만 이는 전체 VLA 미세조정 규모라 상위 불문 설계엔 과대) 종합 — **상위 VLM 자체는 새 로봇 데이터가 거의 필요 없어야 한다**(좌표가 로봇 불문이므로). 50/200편 few-shot은 상위가 아니라 **하위 실행/JCR 쪽의 로봇별 미세조정**(TCP 오차·그리퍼 타이밍 보정)에 주로 쓰는 것이 이번 조사의 1·2절 결론과 맞는다. 상위 LoRA를 굳이 새 로봇마다 돌린다면 MolmoAct 선례(LoRA, 가벼움)만큼만.
- **LoRA 설정**: 기존 Qwen3.5-35B-A3B LoRA 설정을 그대로 재사용(랭크·타깃 모듈 변경 불필요) — 새 로봇은 입력(`robot:`/`camera:` 줄)과 출력 해석(코드 쪽 TCP/폭표)만 바뀌므로 LoRA 하이퍼파라미터를 로봇별로 바꿀 근거가 없다(단순성 원칙).
- **판정 기준**: leave-one-robot-out 영샷이 50편 적응과 "연결 손실 ≤ 5%p" 수준으로 가까우면(NOW.md 결합 기준과 동일 철학 적용), 상위는 정말로 로봇 불문이라는 가설 1(아래 4.3)이 지지된다. 영샷과 50편의 차가 크면 하위 실행 코드(온보딩 도구 산출물: TCP·폭표·reach map·ready pose)의 정확도부터 의심한다 — "상위를 더 학습"하기 전에 "하위 설정이 맞는지"를 먼저 재확인하는 순서가 복잡도를 늘리지 않는 디버깅 순서다.

### 4.3 proprio/로봇-상태 입력 — 기본 NO
- 0-5절과 동일. 추가할 근거가 강해지는 경우(예: 블라인드 구간에서 접촉/파지 상태를 상위가 직접 판단해야 한다는 결정이 나올 때)만, **JCR 쪽에 한정해** 재검토한다. 상위 입력 포맷(4캠+robot:+camera:)에 상태 필드를 넣지 않는다.

## 5. 확인 못한 것 / 추가 조사가 필요한 것
- WebSearch 도구가 세션 예산(200/200)을 이미 소진한 상태에서 시작해, 이번 조사는 WebFetch(직접 URL 접속)만으로 진행했다. 따라서 "최근 1.5년 내 그리퍼 폭 자동 보정·역도달성 지도 전용 신규 논문" 탐색은 검색 없이는 한계가 있었다 — 3.3·3.4는 설계 권고로 대체했다.
- Isaac Lab URDF 임포터의 정확한 현재 기능(자동 질량/관성 추정, 원격측정 등)은 미확인.
- HAMSTER GitHub 별수·라이선스는 공식 페이지 HTTP 429로 미확인.
- π0.5의 패딩/정규화 구현 세부는 초록만 확인, 본문(코드 또는 논문 표)까지 내려가 보지 못했다 — 다음 조사에서 openpi 저장소 코드를 직접 보면 강한 근거로 올릴 수 있다.

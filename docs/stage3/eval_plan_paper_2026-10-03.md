## 트랙 1. 자체 평가 벤치마크 — **l9_test** (7축, 전부 L9 v2 보류에서 뽑는다)

사용자 지시(10-03): 자체 평가 스위트의 이름은 **l9_test**다. 전부 L9 v2 양산의 보류(hold-out)에서 뽑으며,
L8-X를 v2 규약으로 재라벨하는 축(옛 §1.8 "L8-X-v2")은 **뺀다** — l9_test는 L9 v2 자산만 쓴다(L8-X 자산은
트랙 2에서 π0 계열 비교용으로만 쓰고, l9_test 안에는 넣지 않는다).

l9_test의 7축: (1) HOLDOUT_FROZEN, (2) eval_ood(처음 보는 물체·방), (3) unseen robot, (4) camera variation,
(5) perspective/directional, (6) articulated skills, (7) bimanual/handover.

공통 규칙(기존 사전등록 관행 재사용):
- **평가 세트는 참값 계획으로도 성공한 편만 포함**(OOD-O 정책, `docs/stage3/results/ood_o_eval_l8s.md`). 참값 실패 편이 섞이면 완벽한 모델도 상한이 생긴다.
- **폐루프 성공 기준** = L9 v2 과제별 완전 성공(관절 각/변위 임계, 관절 걸음 ≤ 0.04 rad 단언 유지).
- **지표**: 성공률(SR) + 보조로 점 오차(ego: 픽셀 중앙값·20 px 초과율, 3D 과제: mm 중앙값·20 mm 초과율) — HCAM8/TP1에서 쓴 "평균 대신 중앙값+초과율" 규칙을 그대로 쓴다(시드별 평균 흔들림이 수~20 mm라 평균은 부적합, E-VIEW8 근거).
- **CI**: 에피소드(또는 행) 단위 짝 부트스트랩 10,000회, 시드 0 고정(L8-X류는 2,000회, TP1 관행).
- **표본 한계**: 한 축의 유효 평가 편이 200 미만이면 결과에 "표본 한계" 태그를 붙인다(TP1 §5 관행).
- **공개 패키지**: 각 축마다 (a) 보류 정의/시드 목록 JSON, (b) 빌드·채점 스크립트, (c) 장면 자산 해시(재생성 가능하면 자산은 안 올리고 생성 코드만). 전체는 `docs/stage3/eval_release/l9_test/` 아래 모을 것(지금은 미생성 — §4 "지금 준비" 참조).

### 1.1 L9 v2 HOLDOUT_FROZEN (표준 보류)
- **정의**: `alloc9.HOLDOUT_FROZEN`(동결 10개 과제 정의) ∪ GP2 해시 정의(`sha256("gp2:<task_id>") % 5 == 0`) ∪ `collect/holdout` 폴더 정의. 로봇은 게이트 통과분(ffw_sg2, franka_mast)만 — `alloc9.ROBOT_GATE_CLEARED`.
- **편 수**: 지금 보류 풀 1,938편(정의 53개, TP1 변경 2 측정). 폐루프는 비용이 커 **정의당 시드 순 최대 10편**(TP1 규칙 그대로) = 상한 530편. 오프라인 토큰 평가(답 형식·픽셀 오차)는 전수 가능.
- **성공 기준/지표**: 과제별 완전 성공 + 라벨 정확도(point_2d, approach 계열, rot ±1).
- **주의**: R1 Pro·G1은 게이트 미통과라 이 축에는 안 들어간다(§1.3이 그 역할).

### 1.2 eval_ood (처음 보는 물체·방)
- **물체**: OOD-O 기존 58편(13종, 참값 성공만, 시드 70160+). 논문용으로 2차 보충(`plan_ood_o_eval_topup.json` 같은 방식)으로 ≥90편까지 늘리는 것을 권장(물체당 최소 2편 유지).
- **방**: 전용 room-only 분할이 아직 없다 — CL15가 쓴 "학습 방·HDRI·재질과 교집합 0" 검증(`overlap.json`)을 재사용해 room-OOD 서브셋을 새로 뽑아야 한다(≥30편, 1.5~2 GPU-h 렌더).
- **지표**: SR, 접근 3D mm 중앙값/20 mm 초과율. 실패 원인 분류(OOD-O §"참값 실패 원인 분류" 표 형식 재사용 — tipped/도달밖/놓기실패 등).

### 1.3 unseen robot (leave-one-robot-out)
- **핵심 사실**: `alloc9.ROBOT_GATE_CLEARED = {ffw_sg2: True, franka_mast: True, r1pro: False, g1: False}`(10-03 01h). R1 Pro·G1은 **이미 자연스럽게 학습 빌드에서 빠진다** — 추가로 뭔가 지울 필요 없이 이 플래그를 논문 평가 시점까지 동결하면 깨끗한 leave-one-robot-out이다.
- **편 수**: R1 Pro·G1 각각 온보딩 검증(`docs/stage3/results/onboarding_tool.md`) 통과한 pilot 에피소드(pilotG 등) 중 참값 성공분을 평가 전용으로 모은다. 목표 로봇당 ≥30편(부족하면 시범 추가 렌더, 로봇당 ≈1 GPU-h).
- **지표**: 로봇별 어댑터만 바꾼 zero-shot SR(상위 LLM 미세조정 없음, point+height 의도 → 그 로봇 cuRobo/그리퍼 폭 테이블로 변환).
- **위험**: 두 로봇의 게이트가 논문 전에 True로 바뀌면 더 이상 "unseen"이 아니다 — 평가 시점에 그 상태를 캡처해 기록해야 한다.

### 1.4 camera variation (머리 높이/피치/화각, 3인칭, 기울어진 카메라)
- **소스(l9_test 본축, L9 v2 네이티브)**: E-HCAM8 보류 기하 세트 — L9 v2 양산 안에서 동전으로 뽑은 무작위 기하 편의 보류분(목표 900편, H1/H2, NOW.md §2). 중앙값·20 mm 초과율로 처음 보는 기하/기체(Franka 받침대 머리)에서 퇴행 없는지 본다(E-HCAM8 사전등록 §0 질문 그대로).
- **3인칭 축**: TP1의 L9 v2 3인칭 보류 행(on/off 비열등 결과, §1.5와 지표 공유) — 역시 L9 v2 양산에서 나온다.
- **편 수**: HCAM8 보류 900(목표, 진행중 — §4 "지금 준비" 아님, GPU 필요), 3인칭 보류는 TP1 빌드 산출물 재사용(렌더 불필요).
- **참고(l9_test 밖, 트랙 2 보조로만)**: TP1 평가에서 참고 지표로 쓰던 "L8-X 7세트"는 L8-X(옛 자산)라서 l9_test에는 넣지 않는다 — 필요하면 트랙 2의 π0 계열 비교 쪽에 남긴다.

### 1.5 perspective/directional 서브셋
- **소스**: TP1 보조 문항 P(로봇 기준 방향 점찍기)·Q(관점 QA)·Y(카메라-로봇 상대 요) — 층마다 최대 2,400문항, 머리 정면/기울임/3인칭 층 × P·Q·Y. 방향 단어가 있는 지시의 3인칭 보류 행(`l9_eval_tpdir`)도 포함.
- **지표**: 관점 정확도(P는 정답점이 반대방향점보다 가까움, Q는 정답 일치), 좌우 혼동률. 전부 시뮬 참값에서 만든 보조 문항이라 **다시 렌더하지 않는다**(GPU 0) — TP1 빌드가 이미 만든 자산을 재사용.

### 1.6 articulated skills
- **소스**: L9 v2 관절 스킬 1단계(서랍·문·미닫이·노브·버튼·밀기, 16정의+복합 3–4, AI Worker+Franka, R1 Pro 다음·G1 제외). 관문 = 정의당 ≥20편 시범에서 "사용 가능 성공률"(성공 ∧ 관절 걸음 ≤ 0.04 rad) ≥ 0.70.
- **편 수**: 양산 큐에 들어간 뒤 정의당 보류 10~20편을 분리(생산 중 홀드아웃 비율 지정) → 목표 ≥150편(17정의 × ~10).
- **지표**: 관절 각/변위 성공 + `point2`(축 이동 목표) 라벨 정확도.
- **상태 의존**: 10-02 스모크/시범 단계였다(`docs/stage3/results/l9v2_articulated.md`) — 논문 평가 시점까지 양산 큐 진입·보류 분리가 끝나야 한다. 안 끝나면 이 축은 "진행 중 결과"로 축소 보고.

### 1.7 bimanual / handover
- **소스**: `docs/research/bimanual_datagen_2026-10-02.md` — 초안 12개(핸드오버 6·양손 들기 3·고정+담기 2·동시배치 1) 대비 3배 확장 ≥36개. 스키마에 `arm: left|right` 두 개 사용. **10-03 기준 설계만 있고 양산 미착수**(NOW.md 진행 목록에 없음).
- **편 수**: 양산 완료 후 과제군당 보류 ≥5편 → 목표 ≥180편.
- **지표**: 핸드오버 성공(전달 완료), 충돌/놓침률, 두 팔 동시성 오차(둘 다 완료까지 걸린 시간 차).
- **위험**: 이 축은 본 모델 완성 시점까지 데이터가 없을 수 있다 — §3 순서에서 가장 늦게 배치하고, 없으면 논문에서 "진행 중/다음 판"으로 명시.

### 2.2 π0.5 변형·우리 모델 행
- **π0.5 base(무학습)**: openpi 공개 가중치, 벤치별 정규화 통계만 적용(LIBERO만 예외: π0.5-LIBERO 공식 미세조정 가중치를 "참고" 행으로 별도 표기, 같은 열에 안 섞음).
- **π0.5/π0 벤치별 미세조정**: 공식 체크포인트가 있는 벤치(LIBERO π0·π0-FAST, RoboCasa365 π0.5)만 "공식 미세조정" 행으로 인용 — 우리가 직접 π0.5를 벤치마다 미세조정하지는 않는다(가설 1 검증용 E-VB1은 10-01 밤 사용자 지시로 중단·보존, 이 논문 트랙과는 별개).
- **우리 zero-shot**: 최종 모델, 벤치별 전용 미세조정 없음, 어댑터만(E-LIB0b 교훈 — 어댑터에 로봇 실제 설정값을 넣는 것만으로 2 %→14 %, 이건 "저격"이 아니라 공정 조건 유지다).
- **우리 벤치 미세조정**: LIBERO만 이미 분기 존재(E-LIBFT, 57 %/51 %-Plus) — 최종 모델 기반으로 다시 만들 필요(기반 체크포인트가 바뀌므로).

### 2.3 같은 조건 규칙 (저격 금지)
- **벤치 저격 금지**: 벤치별로 디코딩·재시도·프롬프트를 따로 조정하지 않는다. 어댑터가 받는 것은 **그 벤치의 실제 로봇 설정값(그리퍼 폭·작업대 높이·카메라 fx 등)뿐** — 이건 공정 조건이고(E-LIB0b), 성공률을 노려 벤치마다 다른 로직을 넣는 것은 금지.
- **어댑터 입력 경계**: 어댑터는 "그 벤치의 실제 로봇" 값만 받는다. 시뮬 내부 정답 상태(물체 자세 등)는 받지 않는다 — 이미 E-SIM0/E-LIB0에서 지킨 경계 그대로.
- **3인칭 허용 범위**: 사용자 10-02 "3인칭 금지를 내가 풀게"로 이 트랙(π0 계열 비교)에는 3인칭을 허용했다. 트랙 1(자체 벤치)의 3인칭 금지(머리+쓰는 팔 손목만)는 그대로 — 두 트랙의 규칙이 다르다는 것을 논문 방법 절에 명시해야 한다.

### 2.4 BEHAVIOR·PolaRiS/DROID-sim 재평가

**BEHAVIOR-1K**: 추가 가치는 크다(1·2등이 π0.5 기반, SR 12.4 % — π0.5 계열 논문이 실제로 쓰는 벤치). 그러나:
- 비용 "가장 큼"(EVAL-evaluation-design.md §2.5 분류 그대로): Isaac Sim 5.1 + Isaac Lab, 이동형 양팔(현재 우리 로봇은 고정 베이스 단일/두 팔) — **정책 구조가 안 맞는다**(이동 베이스 제어가 우리 스킬에 없음). 자산 43 GB는 이미 받아 뒀다(`/data/harvest/behavior`).
- **권장**: 이번 논문에는 넣지 않는다. 넣으려면 이동 베이스 스킬을 새로 만들어야 해서 "방법론 과도 복잡화 금지" 원칙과 충돌한다. 다음 논문감(이동 로봇 확장) 후보로 미결 기록만 남긴다.

**PolaRiS/DROID-sim**: 비용은 중간이다.
- 막힌 지점(E-POL0)은 `render_float` 전용 환경의 PhysX GPU 파이프라인 실패였다. L9가 이미 쓰는 Isaac 5.1 + Lab 2.3 chroot(`ir_run.sh`, 7a2a에서 양산용으로 매일 돌리는 길)는 **같은 Isaac 판본이고 이미 검증된 경로**다 — 처음부터 새로 까는 게 아니라 이미 작동하는 chroot에 PolaRiS 패키지만 얹는 재시도다.
- **권장**: 스모크(1 GPU-h 내 Franka 1팔 과제 1개 성공/실패만 확인) 1회를 §3 순서 중 "낮은 비용 축" 단계에 넣는다. 통과하면 pi0-FAST-DROID 공식 체크포인트 대비 우리 zero-shot을 잰다(Franka 한 팔 과제만, 우리 팔은 한 팔 가능 과제로 제한 — 조사표 D항 원칙 그대로). 스모크 실패면 깨끗이 드롭하고 논문에 "시도·실패" 한 줄만 남긴다(이미 pol0_hold.md에 그 상태가 있다).

**CALVIN 등**: §2.1 표의 제외 사유 그대로 — 흔히 쓰이지만 비용이 싸지 않아 이번 논문에는 안 넣는다.

**순서 원칙**: 본 모델 학습(78dc GPU0–3)은 끝까지 손대지 않는다. 완성 전에는 선행 조건 칸의 §4 준비 작업만 돌린다(렌더 카드 여유분·CPU). 완성 즉시 위 표 순서로 비는 카드마다 항목을 배정한다.

### 6.2 계층형 포인팅 파일럿에 공정한 벤치 판별

LIBERO/SimplerEnv의 **폐루프 성공률**은 포인팅(어디를 볼지)과 저수준 제어(어떻게 움직일지)를 한 수치에 뭉친다. HAMSTER·RoboPoint·MOKA 같은 계층형 시스템은 이 문제를 알고 다음처럼 쪼개 평가했다(원 논문 설계, 재확인 못 함 — 추정 포함):
- **HAMSTER**: 상위 VLM(경로 그리기)과 하위 시각 서보 정책을 분리 — (a) 실로봇 다기체 조작 성공률, (b) 웹/로봇 영상에서 상위 포인팅 정확도만 따로 재서 "하위를 바꿔도 상위 전이가 유지되는가"를 봄.
- **RoboPoint**: 순수 포인팅 모델 — 자체 합성 벤치(관계형 집기점) + RefCOCO류 그라운딩 + 고정 저수준 컨트롤러 위 실로봇 집기 성공률.
- **MOKA**: 학습 없는 프롬프팅(GPT-4V가 키포인트 표시) — 시뮬 벤치 수치가 전혀 없고 고정 저수준 원시 동작 위 실로봇 성공률만.
- **MolmoAct**: 깊이→궤적→행동 토큰이 **같은 자기회귀 모델**이라 "계층"이되 분리된 두 모델은 아님 — 그래서 LIBERO/SimplerEnv e2e 수치와 별개로 RoboRefIt·Where2Place급 포인팅 벤치도 따로 보고.

**결론(이 프로젝트에 적용)**: 본 모델처럼 상위(포인팅+높이 의도)와 하위(코드 깊이→IK)가 **진짜로 분리**된 시스템은, e2e 성공률만으로 π0.5(단일 flow 모델)와 비교하면 저수준 실행기 차가 섞인다. §2.3의 "같은 조건 규칙"(어댑터는 실제 로봇 설정값만, 저격 금지)이 이미 이 문제의 절반(실행기 조건 통일)을 푼다. 남는 절반은 **포인팅 자체의 정확도를 분리해서 보는 것** — l9_test §1.1·1.2(점 오차: px 중앙값·초과율)와 §G(Where2Place·RefSpatial-Bench, `main35_recipe.md`)가 이미 이 역할이다. 따라서 LIBERO/SimplerEnv 폐루프 성공률(e2e, 트랙 2)과 Where2Place/RefSpatial-Bench류 포인팅 정확도(분리, l9_test §G)를 **둘 다** 보고하는 것이 계층형 파일럿에 공정하다 — 하나만 쓰면 어느 쪽으로든 왜곡된다.

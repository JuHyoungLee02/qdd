## 2. 데이터 가용성 (확인 결과, 2026-10-01 05시경 KST)

- L8S 원본: `/data/harvest/out/teach_l8d/l8s_prod/train/<fixture>/<task>_s<seed>/`, 9,133편(11 fixture 묶음).
- 편마다 남아 있는 것:
  - `joints.npz`: q (T×31, 20 Hz, dt 0.05), base, arm_cmd_offset_ik, arm_target_torque_vel, names. 관절 궤적은 있다.
  - `calls/cNNN/`: **결정 시점(편당 6–8회)에만** 머리 png(원 표시 전·후), 오른손목 png, 머리 깊이, cams.json, prompt, reply.
  - `labels.jsonl`, `scene.json`(지시문 포함), `meta.json`, `result.json`.
- 연속 프레임 `frames/`: 1,389편(15 %)에만 있다.
  - 편당 약 4 Hz이고 크기는 1336×376이다. 두 카메라를 가로로 이어 붙인 미리보기로 보이며, 아직 확인하지 않았다.
- 물체 자세의 시간 궤적은 없다.
- **결론**: π0.5 학습에 필요한 연속 관측(머리 + 오른손목, ≥ 10 Hz, 행동과 시각 정렬)이 없다. 행동(20 Hz 관절)은 있다.
  - 그래서 **재생 렌더가 필요하다**. 방법:
    1. 편을 만든 작업 줄로 세계를 다시 짓는다. E-M35CL `sched.py`와 같은 방식이다.
    2. 기록된 팔·집게 관절 목표를 물리로 재생한다.
    3. 매 걸음 머리·오른손목을 렌더한다.
  - 재생은 물리로 한다. 매 걸음 `write_joint_state`로 덮어쓰지 않는다(Task C 함정: 파지가 교란됨).
  - 재현 검사: 편 끝 물체 위치가 기록 결과와 ≤ 1 cm이고 성공 여부가 같은 편만 쓴다. 불일치 비율을 보고한다.
- 렌더 비용 추정(검증 전): 편당 약 11 s 시뮬 × 9,133편. 카메라 2대·10 Hz면 렌더 카드 한 장에서 레인 4개로 시간당 약 400편(JCR d1 실측)이다.
  - 따라서 카드 1장으로 약 23시간, 카드 2장으로 약 12시간이다.
  - 렌더 카드는 NOW §3을 따른다. L9 양산이 우선이고 GPU_WANTED 양보 규칙을 지킨다.

## 3. 설계 (라이선스가 풀리면 이대로 등록; 결과 전 고정)

### 3-1. 질문과 판정
- 질문: 같은 L8S로 미세조정한 VLA 단독과 Fly-by-Wire 중 어느 쪽의 폐루프 성공률이 높은가?
  - Fly-by-Wire = 본 35B 최적 체크포인트 + 현재 실행기, JCR이 준비되면 JCR.
- 판정(세트마다, 같은 편끼리 짝):
  - **FBW_BETTER**: 성공률 차(FbW − VLA) ≥ +10 %p이고, 짝 부트스트랩(10,000회) 95 % 구간의 하한 > 0.
  - **VLA_BETTER**: 반대 방향으로 같은 조건.
  - **구분 안 됨**: 나머지.
- 가설 1 지지 = 두 세트(새 물체, L8S 검증) 모두 FBW_BETTER.
- 한 세트만 FBW_BETTER이면 '부분 지지'로 적는다.

### 3-2. 공정성 (같게 두는 것)
- **학습 데이터**: 같은 L8S 에피소드. main35의 학습 편 = L8S 전체 − `val_episodes.txt` 222편이다.
  - 서랍 b3d와 고리는 main35와 같은 규칙으로 뺀다.
  - VLA는 재현 검사를 통과한 편만 쓴다. 빠진 편 수를 보고한다.
- **카메라**: 머리(원 표시 없음 원본) + 오른손목만. 3인칭·어안·왼손목은 쓰지 않는다.
  - FbW 쪽 머리 원 표시는 상위 입력 형식이라 그대로 둔다. 원 표시는 영상 위 표시일 뿐 정보량 차이가 없다고 보고, 한계에 적는다.
- **평가 세트·시드·판정기**: E-M35CL의 `groups.json`을 그대로 쓴다.
  - 세트는 OOD-O58 58편(새 물체)과 L8S 보류 편(`val_episodes.txt`, 제외 규칙 동일)이다.
  - digest가 E-M35CL과 같아야 한다.
  - 성공은 같은 실행기 환경의 `env_success`로 정한다. 주 지표는 참값 성공 편 기준이다.
- **폐루프 한도**: 동작 120 s로 둘이 같다.
  - 상위의 호출 30회 상한은 상위 쪽에만 해당한다. VLA는 시간 한도만 둔다.
- **시작 자세**: L8S 변경 21·26의 ARM_START와 머리 45°. 관절 걸음 ≤ 0.04 rad 규칙은 VLA 출력에도 똑같이 적용한다(초과분은 자름, 자른 틱 수를 보고).

### 3-3. VLA 설정 (선택지 (a)일 때 π0.5, openpi 공식 미세조정 레시피 기준)
- 출발: `pi05_base`.
- 입력: 언어 지시(scene.json `instruction`) + 머리·오른손목 영상 224 + 상태(오른팔 7 + 집게 + 리프트 + 머리 2).
- 출력: 관절 목표 청크(오른팔 7 + 집게). 정규화는 공식 기본값을 따른다.
- 예전 Task C 함정 3종을 먼저 확인한다(`project_pi05_train_v6`):
  - 델타는 팔 관절만 쓴다. 상수 채널(머리·리프트)은 절대값으로 둔다.
  - 델타 통계는 float64 전용 도구로 계산한다. lerobot `recompute_stats`는 쓰지 않는다(float32 버그).
  - 평가 정규화에는 학습셋 통계(체크포인트 안 전처리기)를 쓴다.
- 체크포인트 고르기: 학습에 안 쓴 L8S 검증 분할(보류 222편과 겹치지 않는 편 단위 3 %)의 폐루프 성공률로 고른다.
  - 후보는 저장 체크포인트 중 3개다. 오프라인 MAE만으로 고르지 않는다(Task C 실측: MAE 1위가 폐루프 5위).
  - 평가 세트(OOD-O58·보류 222)로는 고르지 않는다.
- 선택지 (b)·(c)이면 각 공식 미세조정 스크립트의 기본값을 쓰고, 입력·출력·세트는 위와 같다.

### 3-4. 자원 계획 (정해 둔 것, 아직 실행하지 않음)
- **변환**(CPU): 재생 렌더 결과를 LeRobot v3 형식으로 바꾼다. 7a2a 파드 CPU를 nice 19로 쓴다.
- **재생 렌더**: 렌더 카드는 L9에 양보한다. 쉬는 렌더 카드만 쓰고, GPU_WANTED가 생기면 한 편 안에 비운다.
- **학습**: 본 35B 판정이 끝난 뒤(≈14:20 KST) 78dc GPU0–3에서 DDP로 돌린다.
  - 체인은 `main35` 판정 끝 표식을 기다린다. 본 학습 파일은 읽기만 한다.
  - 코드 사본은 `/data/harvest/code_vb1_<커밋>`에 둔다.
- **평가 렌더**: L9 양산·JCR과 겹치지 않게 쉬는 렌더 카드만 쓴다.
  - 정책 서버는 렌더 금지 카드(x3 GPU0 등)에 둔다.
  - 영상은 `/data/harvest/videos/vb1/`에 머리·오른손목 10 fps로 저장한다.

## 4. 버리기 전 재검증 (board 규칙 6)
VLA 기준선이나 FbW 중 한쪽을 '진다'고 결론 내기 전에 결과 문서에 다음을 적는다.
- (a) **설계가 공정했나.**
  - 재생 렌더의 재현 불일치가 VLA 학습 데이터를 깎지 않았나.
  - FbW의 상위는 공개 점 데이터 6.3만 행을 더 봤다. 이 비대칭을 적는다.
  - 카메라 해상도, 120 s 한도가 VLA에 짧지 않았나(시간 초과 실패 비율).
- (b) **지금 최선의 시도였나.**
  - VLA 쪽: 체크포인트 3개, 청크 재생 스무딩(팔 EMA 0.5, Task C에서 쓴 것)과 재질의 주기를 한 번 바꿔 본다.
  - FbW 쪽: 최적 체크포인트, 루프 차단(E-M35CL2)을 켠 경우와 끈 경우.
- 한쪽이 재검증에서 살아나면 기존 결론을 바로 뒤집지 않는다. 같은 조건으로 한 번 더 짝 비교한 뒤 정한다.

    - 조정자가 평가 카드 7a2a GPU2를 후보로 제시했지만, DEVICE_LOST 이력 때문에 렌더 금지 카드다(`tools/teach_l8d/isaac.sh`가 거부한다).
  - 카드마다 두 조건이 모두 맞을 때만 레인을 띄운다.
    - `/data/harvest/out/l9/GPU_WANTED`에 그 카드가 없다(빈 파일이면 전체로 본다).
    - 그 카드에 VB1이 아닌 프로세스가 없다.
  - 둘 중 하나가 깨지면 지금 편만 끝내고 비운다. 비운 카드는 `GPU_FREED`에 한 줄 남긴다.
  - 레인 수는 파드 CPU 사용률을 보고 정한다(7a2a 쿼터 32코어, x2 12코어).
  - 스모크(편 10개)로 편당 시간을 먼저 재고, 그 값으로 전체 시간 추정(23시간)을 고친다.
- **변환**(CPU, GARO lerobot venv)
  - LeRobot v3 형식, 10 fps, `observation.images.top`(머리)·`observation.images.wrist_right`(오른손목).
  - 왼손목은 넣지 않는다. π0.5 기본 동작대로 −1로 채우고 마스크 0이다.
  - 행동 통계는 델타(청크 50, action[t+k] − state[t], 팔 7축만) 기준으로 float64로 직접 계산한다. lerobot `recompute_stats`는 쓰지 않는다.
- **학습**(78dc GPU0–3)
  - 시작 조건: main35 판정 끝(`/data/harvest/out/main35/MAIN35_DONE` 또는 main35.log의 JUDGE_FAIL·EVAL_INCOMPLETE) + 4장이 비어 있음(메모리 < 1 GB) + 데이터 변환 끝. 본 학습의 파일·프로세스는 읽기만 한다.
  - 레시피: Task C v6과 같다(`/data/juhyoung_pi05/train_taskc_v6.sh`).
    - `pi05_base`, LR 2.5e-5, warmup 1k, batch 16 × 4, bf16, gradient checkpointing, 이미지 증강, seed 1000.
    - 델타 행동은 팔 7축만, 집게는 절대값이다.
    - rename_map 재주입 래퍼 `lerobot_train_v6.py`를 쓴다.
  - **30k 걸음, 5k마다 저장.** 근거: Task C는 60k 이후 정체였고, v6은 40k였다. 이번 데이터는 약 80만 프레임이라 30k × 64 ≈ 2.4바퀴다.
- **VLA 추론**
  - 10 Hz로 50 청크를 예측하고 앞 10개(1 s)를 실행한 뒤 다시 묻는다. 청크 행 사이는 20 Hz로 선형 보간한다.
  - 관절 걸음 ≤ 0.04 rad 규칙은 같은 ARM_DQ·ARM_BAND 제한을 거쳐 지킨다.
  - EMA·앙상블은 쓰지 않는다. 4절 재검증에서만 팔 EMA 0.5와 재질의 5를 쓴다.
- **체크포인트 고르기**
  - 후보는 20k·25k·30k다.
  - 고르기 분할에서 참값 성공 편 60개(시드 오름차순 고정)를 폐루프로 돌려 성공률 1위를 고른다. 같으면 늦은 걸음을 고른다.

### `oracle` 필드는 학습·채점 정답으로 쓰면 안 된다 (메인 E3-lite 발견)
풀의 `oracle`(dir_xy·dir_z·mag_coarse·fine_dir·phase_choice 등)은 **계획기의 명령 TCP 궤적과 단계 타이머**에서 뽑은 값이다. 같은 관측 상태에서도 계획기 내부 상태(명령 자세가 실제 TCP보다 앞서 있음, 단계 경과 시간)에 따라 답이 달라지므로 **관측(텍스트 상태 + 이미지)만으로 결정되지 않는다**. 정답으로는 T14 결과 기반 라벨(`labels/`)을 쓴다. `oracle`은 라벨러가 "묻지 않는 나머지 성분"을 채우는 기준과 참고용으로만 남긴다.

## 2. 풀을 다시 만든 이유 (첫 풀 13:32–13:53 UTC, 지우지 않고 보존)
첫 풀 120편은 결함 없이 끝났지만, T14 라벨러가 쓰는 **재실행 복원**(3.2절)이 첫 풀과 비트 단위로 맞지 않았다. 각 편 앞의 고정 선행 실행을 첫 lift 스냅샷에서 끊었더니 PhysX가 쌍별 접촉 자료(머그–탁상 등)를 리셋 너머로 들고 가, 다음 편이 이력에 따라 조금씩 달라졌다(ep2000 재실행 상태 차 최대 0.0099). 각 프로세스의 첫 편(2000·2030·2060·2090)은 선행 실행 자체가 프로세스 첫 실행이라 더 크게 달랐다(0.002–0.016). 선행 실행을 첫 carry 스냅샷에서 끊고(6가지 이력 뒤 다음 편 비트 동일) 프로세스 시작 때 한 번 더 돌리도록 고친 뒤 풀 전체를 다시 만들었다(14:00–14:11 UTC). 첫 풀은 `/data/harvest/data/pool_superseded_liftcut/`에 두었다(`SUPERSEDED.txt`에 설명, 프로세스 첫 편 4개는 그 안의 `_superseded_first_in_process/`). 옛 선택 기준으로 돌던 자체 점검 조각도 `…/selfcheck_ambiguous_only_stratum/`에 두었다. 라벨에 필요한 필드가 빠진 것은 없었다.
- 추가(15:0x UTC): 두 번째 풀의 **프로세스 첫 편 4개**(2000·2030·2060·2090)도 재실행과 달랐다(라벨 행 `replay_obj_mm` 최대 약 6 mm, open 단계). warmup이 선행 실행 하나뿐이라 "선행 실행 뒤 선행 실행" 이력이 됐기 때문이다. warmup = 선행 실행 + DEV 0 P0 완주로 고치고(두 이력 대조 차 0.0) 그 4편만 다시 만들었다. 옛 4편과 그 풀로 돌던 라벨·자체 점검 조각은 `pool_superseded_liftcut/v2_run2_*`에 보존. 다시 만든 뒤 라벨·자체 점검 첫 6편의 재실행 차는 전부 **0.0**(상태·물체 위치).

원인 추적:
1. 되읽기: 쓴 직후 관절·물체 상태는 저장값과 **정확히 같다**(차 0). 관절 한계 위반 없음.
2. 첫 물리 스텝(10 ms)에서 이미 그리퍼 **보조 손가락 관절(joint2–4, 강성 2)**이 원래 궤적과 0.019 rad 다르게 움직인다 → 접촉 해가 다르다.
3. 쓰고 1·2·5 물리 스텝을 돌려 접촉을 만든 뒤 다시 쓰는 방식(prime)도 편차가 **소수 넷째 자리까지 같다** → 쓰기(순간 이동)가 쌍별 접촉 캐시를 비우고, 원래 궤적은 데워진 캐시로 계속한다. 쓰기로는 되살릴 수 없는 상태다.
4. PhysX enhanced determinism 켬: 결과 동일(효과 없음). GPU PhysX(참고): 같은 close 시점 1.59 mm.
5. 같은 상태를 두 번 복원한 것끼리는 0.0(복원 자체는 결정적). 문제는 "원래 궤적 대비"뿐이다.

v2에서 커진 까닭: 복사한 로봇 설정의 보조 손가락은 강성 2로 거의 접촉에만 끌려 다니고(v1은 보조 손가락에 주 손가락 게인을 줬었다) 파지가 약해, 접촉 해의 작은 차이가 머그 위치 mm로 커진다.

### 3.2 재실행 복원: 합격 — 채택
- 방법: 스냅샷 k로 돌아갈 때 상태를 쓰지 않고, **에피소드를 리셋부터 오라클 플래너로 다시 돌려 k에서 갈라진다.** 쓰기는 에피소드 자체의 리셋 한 번뿐이라(원래 궤적과 똑같음) 접촉 캐시도 원래 것이다. Review Focus #5의 "복원은 한 번, 매 스텝 쓰기 금지"를 그대로 지킨다.
- 조건: CPU PhysX는 같은 프로세스 안에서 리셋 + 재실행이 비트 단위로 같다. 다만 앞 실행이 어떻게 끝났는지에 따라 달라지는 경우가 있어(2절) 모든 편 앞에 고정 선행 실행(DEV 0 P0, 첫 carry 스냅샷에서 끊음)을 두고, 프로세스 시작 때 한 번 더 돌린다(`cli_pool.canonical_prefix`, `warmup`).
- 결과(rt_v2e, 10개 시점): **재실행 상태 차 0.0, 0.5 s 유지 편차 0.000 mm**(10/10). 6가지 이력(k2·k3·k9·k20에서 끊음, 완주, 선행 실행만) 뒤 다음 편이 전부 비트 동일.
- 교차 프로세스(풀 생성 프로세스 ↔ 라벨 프로세스): 선행 실행을 고친 뒤 ep2090 10개 시점 **0.0**. 카메라 렌더 유무는 물리에 영향이 없었다(ep2000 켬/끔 결과 동일). 라벨 행마다 `replay_maxabs`(재실행 상태 − 저장 상태)를 남겨 전수 확인한다(labeler.md).
- 비용: 롤아웃마다 선행 실행 + 앞부분 재실행이 붙어 롤아웃당 약 3.5 s(벽시계, CPU 물리).
- `snapshot.restore_state`(쓰기 복원)는 진단용으로 남기고 코드 설명에 v2에서 부정확함을 적었다.

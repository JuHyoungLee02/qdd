## 4. 설계안

### 4.1 트리거 (모두 비초기 호출은 비동기)
| id | 트리거 | 규칙 | 문지기 |
|---|---|---|---|
| T0 | 초기 계획 | 과제 시작. **로봇 정지 허용**(사용자) | 없음 |
| T_fail | M7 FAIL | 항상 호출. 연속 프레임 필수 | "부를지" 건너뜀, 묶음만 결정 |
| T1 | 주기(Hz) | P초마다(P는 §5에서 호출 수 맞춤으로 결정) | 적용 |
| T2 | 정해 둔 순간 | 세션 계약에 적힌 순간(기본: 되돌릴 수 없는 전이 직전 — 놓기 직전, 삽입 시작 직전; CommitFlow·OneTwoVLA의 하위 작업 경계) | 적용 |
| T3a | 자체 판단 — 코드 마감 | 단계 경과 > `D_k`(M7 conformal 마감, 표본 부족 시 1.5×`T_exp_k`) → M7 WARN(C_dead) → 호출 | 적용 |
| T3b | 자체 판단 — 모델 판단 | Jev에 Noul 한 문항 "Given elapsed = {범주} of expected for step '<이름>', should this step have been completed by now?"를 `JevCall`의 감시 질문으로 싣고(00-interfaces §2, 호출 N번에 한 번 싣는 안 포함), **최빈 답이 "예"인 것이 2번 연속**이면 호출. E1 전에는 확률 게이트를 끈다. "예 확률 ≥ 0.7" 게이트는 E1 뒤에 켤 후보 값(00-interfaces §6). 변형 T3b-A: 같은 질문을 Astra에 주기적으로(비용 큼) | 적용 |
| T_stag | 정체 시간 초과 | M7 C_stag 단독 WARN → 호출(Critic in the Loop식). T3와 구분해 기록 | 적용 |

- T3a와 T_stag의 차이: T3a는 **예상 시간 대비 마감**(계획 쪽 정보), T_stag는 **진행이 멈춘 시간**(관측 쪽 정보). plan v4.3의 구분을 유지한다.
- T3b의 사용자 표현 적합성: "이때쯤 결과가 나왔어야 하는데 안 나오네"라는 **자체 판단**은 모델이 내리는 것으로 읽는 게 문자 그대로다(v3/17 B5). 3a는 우리 해석이다. 둘 다 조건으로 둔다.
- **T3b 게이트 문턱 정하는 법(E1 뒤, 00 §14·§15)**: 후보 값 0.7을 그대로 쓰지 않고 RouteNLP식 conformal risk control로 정한다(§3 RouteNLP 행). 질문 유형당 보정 사건이 500개 미만이면(원문 n=100 위반 7.2%) "보장 없음"으로 표기한다. 새 환경에서는 분포 이동으로 보장이 깨지므로(원문 도메인 이동 위반 8.1%) 재보정 표본 수를 기록한다.

### 4.2 문지기 (BRACE 접목)
- 진행 중 요청 한도: 비실패 1개. 실패 호출은 진행 중인 비실패 요청이 있어도 새로 보낸다(이전 요청 결과는 도착하면 버리지 않고 사건 문맥에 붙인다).
- cooldown: 복구 완료 후 2초, 비실패 호출 금지(설정 표 "복구 뒤 cooldown", M7과 같은 값).
- commit 창: Astra 새 계획의 적용 시점은 **M2 R3 하나를 따른다**(D5 2-1). 결정 스텝 경계에서 적용하고, 진행 중 phase의 M6 `effect`가 `irreversible`이면 그 phase가 끝난 뒤 적용한다. 첫 판의 "잡기 닫힘~들어올림 시작"은 M6 `effect`에서 가역(grasp·lift 모두 보상 스킬 있음)이라 따로 두지 않는다. 그리퍼가 닫히는 순간은 grasp/release 전환 보류(1.0 s, 설정 표)가 보호한다. 기다리는 동안에도 직전 확정 행동 유지 + 감속이며 정지가 아니다.
- effort: **기본 low**(정본 §26, user-log 25 — 옛 "잠정 기본 high(다른 작업 발언 근거), low·medium은 측정 조건일 뿐"은 폐기). 실험 축은 **최소 {low, high}**, medium·xhigh·max는 여력 있으면(00-interfaces §9 C5, §5 E-M8a). 지연 예산(2026-09-23 AA 기준 첫 토큰): low 3.0 / medium 5.9 / high 73 / xhigh 198 / max 352초(Artificial Analysis 기준 읽음, 우리가 잰 값 아님) — 날마다 바뀌므로 같은 날 잰다. 실패 호출은 이 시간 동안 M9 아래 층이 로봇을 움직인다.
- 입력 토큰 예산: 이미지 약 3,000~3,600 토큰 + 텍스트 문맥 ≤ 2,000 토큰(아래 표).
- **투표(정본 §28 A5, 잠정 기본)**: T0(정지 허용)에서만 effort low로 K = 3을 **병렬**로 부르고 계획 서명(단계 스킬 열 + 결정 지점 id + 물체 역할) 다수결로 고른다. 셋 다 다르면 검사기 통과 첫 번째 + `plan_unstable` 기록(추가 호출 없음). 비정지 호출(T_fail·T3a·T3b, 그 밖의 T1·T2·T_stag 포함)은 **K = 1** — 투표 때문에 지연을 늘리지 않고, 오류는 M2 검사기·M4 (b)가 잡는다. **effort high 조건에서는 투표하지 않는다**(첫 토큰 약 73 s). K = 3은 설계 선택([가정])이고 E0 Astra 같은 입력 반복 결과로 확정한다(E 문서 §2). E0 판정: low의 계획 서명 불일치가 high보다 유의하게 클 때만(짝 부트스트랩 하한 > 0) 비정지 호출에도 투표를 검토하고, 아니면 A5(T0 전용)를 유지한다. 같은 관측 반복은 분산만 줄이고 증거를 늘리지 않는다(PACT, 정본 §24). 문지기는 K를 바꾸지 않는다(K는 트리거 종류와 effort 조건으로만 정해진다). 계약 쪽 규칙(서명 정의·검사기)은 M2 §4.5.
- **기록(정본 §28 A1·A6)**: 모든 Astra 호출에 요청 원문(이미지 바이트 해시 + 원본), `astra_prompt_id`(템플릿 해시, 실험 도중 불변), 모델 ID(날짜 박힌 스냅샷 ID, 가능하면)와 응답의 모델 식별 필드([가정]: 유무 미확인), effort, 최대 토큰, 사용량, 첫 토큰·완료 시각, 원응답, 검사기 결과, 계획 서명, patch 편집 거리, 트리거 id, 투표 여부·K. 격자 이미지는 배치·해상도·패딩·덧그림 글꼴을 바이트 단위로 고정한다(A2, §4.3).

  3. 정지 시간은 A0를 제외한 모든 조건에서 초기 계획(T0) 시간 + M9 L3 안전 대기 시간만 허용. 그 외 정지가 생기면 구현 결함으로 본다.
  4. [제안] A8(정적 규칙)이 A7(문지기)과 성공률 −2%p 이내이고 비실패 Astra 호출 비용이 같거나 적으면 문지기 단순화를 [결정 필요]로 올린다. A8이 5%p 이상 낮으면 문지기 유지 근거로 기록.
- 시드 3개 이상, 조건당 에피소드 수는 E0 뒤에 정한다(검정력 계산).
- **(정본 §28) 반복 실행과 검정력 사전 등록**: Astra는 temperature 0·seed로 결정성을 얻을 수 없다(추론 모델은 greedy에서도 정확도 최대 9% 변동 — 2506.09501, NeurIPS 2025 Oral). 그래서 Astra 조건(트리거·effort) 비교마다 반복 실행 수와 검정력 계산을 실행 전에 등록한다. 기준은 2%p 차이 검출에 약 9회(2602.07150, MED; ReasonBENCH 2512.07795, MED의 최소 n ≥ 9와 같은 크기). E0 Astra 같은 입력 반복에서 잰 분산으로 조건당 에피소드 수를 다시 계산한다. **단일 실행 비교로 결론 내지 않는다.** effort를 올려도 분산이 준다는 보장은 없으므로(2512.07795) low·high 비교에서 성공률과 함께 분산(반복 사이 표준편차·계획 서명 일치율)을 보고한다. 실험일마다 매일 카나리(E 문서)를 먼저 돌리고, "표류 의심" 날의 결과는 분리 보고한다.
- 순서: T3b의 Jev 감시 질문은 `JevCall`에 실리므로 E0(실제 `JevCall` 크기)·E1 뒤에 돌린다. 확률 게이트 변형(T3b 0.7)은 E1 뒤에만. E-M8b는 기록된 실패 사건으로 **오프라인 병행**(00-interfaces §8).

### E-M8b 다중 프레임 묶음 (오프라인, 기록된 실패 사건 재생)
- 기록된 FAIL 사건 N개(정답 실패 원인·올바른 복구 선택 라벨 = 센서 술어 + 사람 확인)에 대해 Astra를 같은 텍스트로 부르고 이미지 묶음만 바꾼다.
- 조건: G-orig(사용자 기본, 5×2 original) / G-high / S-high(개별 10장, **G-orig과 토큰 같음**) / S-mix(2 high + 8 low) / G+현재 고해상 1장 / 변화 텍스트만 / 텍스트 상태만 / 균일 선택 대 키프레임 선택(격자 안에서).
- 지표: 실패 원인 정답률, 복구 선택 정답률(M9 보기 기준), 첫 토큰 시간, 입력 토큰.
- **판정 기준**: S-high가 G-orig보다 원인 정답률 +5%p 이상(토큰 같음, 구간이 0을 넘음)일 때만 기본값을 개별로 바꾸자고 [결정 필요]로 올린다. 그렇지 않으면 사용자 예시(격자) 유지. "텍스트 상태만"이 G-orig과 −3%p 이내면 이미지 가치가 작다고 보고한다.
- (정본 §28) 사건마다 조건별 반복 호출 수를 사전 등록하고(2%p 검출에 약 9회 기준, 2602.07150, MED) 조건 사이 차이를 반복 사이 흔들림(같은 입력 반복 바닥)과 함께 보고한다. 모든 조건은 같은 `astra_prompt_id` 판본에서 이미지 묶음만 바꾼다(A1).

## 6. 반대 증거와 위험
1. **자주 부르면 나빠질 수 있다**: Learning When to Plan, VLingNav, React When You Need To(v3/05). 비동기라도 새 계획이 진행 중 스킬을 흔들 수 있다 → commit 창.
2. **T3b는 늦을 가능성이 크다**: BAGEN에서 프런티어 모델도 실패 궤적의 마지막 20%에서야 경보. 다만 BAGEN은 "남은 예산 구간 추정"이고 우리 질문은 "끝났어야 하는가" 이진 판단이며 경과·예상을 명시 제공한다(BATS식). 옮겨 올 수 있는지는 모른다.
3. **대부분의 트리거 비교 승자는 학습 게이트**(ASSCG, RARRL, VLingNav, Learning When to Plan). 학습 없는 규칙 트리거가 이긴다는 보장이 없다.
4. **격자 근거의 절제 수치는 오픈 7B 모델(학습 설정일 가능성 높음), 시간 위치 찾기 과제**다(T2SGrid Table 6). 독점 모델에도 적용한 결과는 있다(Table 1의 GPT-4o → +T2SGrid 행, §4.2.1 "further gains", 수치 미추출). 그래도 Astra, 실패 진단 과제, 5×2 배치, 키프레임 칸에서 같은 방향인지는 모른다. Grid2Matrix는 독점 모델도 촘촘한 격자에서 무너진다고 했다.
5. **정지 원칙의 반대 증거**(v3/16): WAM 실물 정밀 끼우기에서 동기 실행 72.5점 > 비동기 40점. 사용자 원칙은 유지하고 정밀 구간 정지 허용을 [결정 필요]로 둔다(plan §5-10).
6. effort high의 첫 토큰 73초 동안 로봇이 할 일(M9 아래 층)이 모자랄 수 있다. (정본 §26: high는 비교 조건이다. 기본 low는 약 3초.)
7. **비용 측면 반대 이론**(2602.09902, ICLR 2026): 공급자 비용 기준으로는 실패 뒤 상향(캐스케이드)이 대개 최적이 아니다. 가정(2모델, 사용자 이탈, i.i.d. 성공)이 달라 설계를 바꾸지 않는다. 사용자 원칙은 유지하고, E-M8a에서 Astra 호출 비용을 성공률과 함께 보고한다.
8. **RouteNLP 보장의 한계**: 주변(marginal) 보장이고 교환 가능성이 필요하며 분포 이동에서 깨진다(원문 명시, 도메인 이동 위반 8.1%). 새 환경 일반화가 핵심인 우리 과제에서는 약점이다. 보정 표본이 단계당 500개에 못 미치면 원문 조건 밖이다.
9. **"실패 즉시 호출"의 반대 증거(정본 §21, D10b)**: CheckVLA Table S6(고정 트리거 수리, 같은 스냅샷) — d_lat = 10(1 s)에서 청크 안 수리 규칙 전부(23.4~31.4%)가 "다음 청크 경계까지 기다림"(34.0%)보다 낮다(우리 읽기, 원문 수치 확인; 원문은 역전을 직접 언급하지 않음). Astra 지연은 몇 자릿수 길다 → A1-wait가 이길 수도 있다. 그래도 **사용자 원칙은 바꾸지 않고** E-M8a 결과로 보고한다.
10. **"매번 부르면 나빠진다"의 근거(정본 §21, D10b)**: Critic in the Loop Dual-System(청크마다 하위 과제 재생성)은 상태 추적 없이 하위 과제 사이에서 진동하고 연체(비닐봉투)에서 멈췄다(§4.2 정성, 그림 6). 단 Critic·기억도 빠진 조건이다. 또 정체 트리거의 효과 근거는 정성뿐(Left cup 1과제, 트리거 절제 없음)이라 A6 계열의 근거 수준은 LOW-MED로 둔다.

### 6.1 M8 평가 기여 차별화 문장(D10b 초안, 정본 §21)
1. "CheckVLA는 같은 VLA를 0.29 s(p50) 지연으로 다시 불러 실행 중 청크 뒷부분만 고치고, 지연은 1 s(10 제어 스텝)까지만 쟀다. 그 끝점에서는 청크 안 수리 규칙 모두(23.4~31.4%)가 다음 경계까지 기다리는 기준선(34.0%)보다 낮았다(Table S6). 저자도 동적 지연 인지 스케줄링을 향후 과제로 남겼다. 우리는 수 초에서 수십 초 걸리는 API 모델(Astra)을 부르는 층에서 트리거 방식을 비교하며, 그동안 아래 층이 로봇을 멈추지 않고 움직인다."
2. "Critic in the Loop는 완료·이상·정체(학습된 진행값 최고점이 180 프레임, 약 20 Hz에서 약 9 s 동안 갱신되지 않음) 때만 상위 모델을 부르지만, 그 호출은 행동 버퍼를 비운 뒤의 동기 호출이고 정체 때는 로봇을 물리적으로 되돌린다(Algorithm 1). 트리거별 절제, 호출 수, 지연은 보고하지 않았다. 우리는 같은 호출 수에서 트리거 방식을 따로 비교하고, 호출이 로봇을 멈추게 하지 않는다."
3. "CheckVLA는 호출 수를 맞춘 주기 재계획과 비교해 시점의 몫(+3.9%p)을 분리했지만 호출 모델과 추론량은 하나였다. 우리는 호출 수를 맞춘 뒤 추론 강도(low~max)를 두 번째 축으로 둔다."
4. "기존 트리거는 관측 쪽 신호다(정체, 행동 조건 예측 불일치). 우리는 계획 쪽 마감(T3a: 성공 롤아웃 conformal 마감 `D_k`)과 모델 자체 판단(T3b)을 같은 호출 수에서 비교해, 사용자가 말한 '이때쯤 나왔어야 하는데'가 관측 쪽 정체와 다른 정보인지 확인한다."
- 주의: "멈추지 않는다" 자체는 CheckVLA에도 있다(트리거 뒤에도 청크 계속 실행). 차별점은 "느린 **별도** API 모델 + 수 초 이상 지연 + effort 축 + 계획 쪽 마감(T3a)·모델 자체 판단(T3b)을 관측 쪽 정체와 같은 호출 수에서 비교".
- 주의(00 §24, D12): **계층 자체는 새로움이 아니다.** JEV-Star(2609.27331)가 "빠른 JEV 선택 + GPT-6 Astra 비동기 계획"을 StarCraft II에서 먼저 했다(계획기 60 게임초 주기 + 사건 호출, 실패·지연 시 이전 계획 유지). 위 차별화 문장 1~4와 함께 JEV-Star를 반드시 인용하고, 우리 차이는 "로봇 실행 중 실패 판정이 불러내는 Astra 호출 + 겹침 호출 합의와 실행 뒤 확인(M4)"으로 좁혀 쓴다.

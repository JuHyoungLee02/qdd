## 0. 결론 요약

1. **방법 = Qwen3-VL 원래 방식 그대로, 이미지 여러 장을 한 메시지에 넣는다(타일 아님).** Qwen3-VL은 원본 해상도 모델이라 **32×32 픽셀 = 시각 토큰 1개**다. 머리 672×376 = **252 토큰**, D405 424×240 = **104 토큰**(각각 시작·끝 토큰 +2) [실측: 입력 토큰 645 → 751]. 타일 한 장(672×616)은 여백 때문에 오히려 **399 토큰**으로 더 많고, 벤치에서도 빠르지 않았다.
2. **지연 병목은 이미지 토큰 수가 아니라 "한 호출 = 8 시퀀스가 같은 이미지를 동시에 들고 들어가는" 구조다.** 손목 한 장을 더해도 N=4 p95는 +0.01–0.03 s(부하 없는 판)뿐이고, 손목 해상도를 28 토큰으로 줄여도 빨라지지 않았다. 반면 **"선행 1 시퀀스를 먼저 보내고, 끝나면 나머지 7개를 병렬로" 보내는 방식(lead)**이 머리+손목 N=4 p95를 **0.29 s(지금 방식) → 0.18–0.21 s**로 줄였다(반복 판·긴 프롬프트 판). 캐시(접두 캐시 + mm 처리기 캐시)를 끄면 지연이 두 배(0.63 s)가 되므로 캐시는 필수다.
3. **권고 배치 [우리 접목]**: `[system] [텍스트 표지 "head camera:"] [머리 672×376, 252 토큰] [표지 "right wrist camera (active arm):"] [활성 손목 424×240, 104 토큰] [상태·질문]`, 원본 해상도(min/max 픽셀 기본값), 이미지 토큰 합 ≈ 360(양팔 스킬 때 ≈ 466). 클라이언트는 lead 계열로 바꾼다. **예상 N=4 p95 ≈ 0.18–0.28 s(H200)** — 지금 머리만 방식(0.27–0.36 s)보다 빠르거나 비슷하다. 실제 길이(824 토큰)보다 긴 1,267 토큰 프롬프트에서도 0.21 s.
4. **사전 규칙 판정(§6.4)**: 머리+손목 모든 배치가 N=4 p95 ≤ 0.33 s("합성 S1에서 가능"). 모드 채택 규칙을 통과한 것은 **leadref**(lead + 뒤 7개는 이미지 바이트 없이 uuid만)이고, 반복 판(사후)에서는 **lead**가 모든 배치에서 가장 빨랐다 → "선행 시퀀스" 구조는 확정, 바이트 생략 여부는 다음 사전 등록에서 정한다. HhW(머리 448×256 + 손목 원본)는 규칙상 대안으로 올라가지만 반복 판에서는 HW와 차이 0.006 s이고 정확도 영향은 모른다.
5. **손목캠 효과 근거**: 원문 수치는 OpenVLA-OFT LIBERO(같은 데이터에서 제3자 시점만 95.3 % → +손목+고유감각 97.1 %, Long 90.7 → 94.5; 손목·고유감각이 섞여 분리 불가, 기간 밖)와 Hsu 외 ICLR 2022(손목 시점이 OOD 일반화를 일관되게 올림, 기간 밖)뿐이다. 주요 VLA(π0.5, GR00T N1, OpenVLA-OFT ALOHA, SmolVLA)는 모두 손목캠을 입력에 넣지만 **손목 절제 표는 내지 않는다**. → §57 결정 실험(잡음 좌표 조건)이 우리 근거가 되어야 한다.

## 2. 선택지별 정리 (질문 1)

### (a) 원래 방식 여러 장 입력 — **채택**
- [원문] Qwen3-VL(2511.21631, 2025-11, **HIGH**, 기간 안): 위치 부호화 "interleaving the t, h, and w components across the embedding dimensions"(Interleaved-MRoPE), DeepStack은 ViT 여러 층 특징을 LLM 첫 3개 층에 더함(문맥 길이 증가 없음). 이미지마다 `<|vision_start|>…<|vision_end|>` 블록이 따로 들어가고 위치 번호가 이어진다. 다중 이미지 벤치(MuirBench) 수치 보고. Qwen2.5-VL(2502.13923, **기간 밖, 기초 문헌**, HIGH): 이미지 토큰 범위 "4-16384".
- [실측] 손목 1장 추가 비용: 토큰 +106, N=4 p95 +0.01–0.03 s(부하 적은 판, lead 모드 0.169 → 0.181).
- [우리 접목] 이미지 앞에 짧은 텍스트 표지("head camera:", "right wrist camera (active arm):")를 둔다(토큰 5–8개). 활성 팔이 바뀌면 표지만 바뀌고 슬롯 위치는 고정(머리 = 1번, 활성 손목 = 2번, 양팔이면 오른손 2번·왼손 3번).

### (b) 타일 한 장 — **쓰지 않음**
- 고정 해상도 인코더(SigLIP 224×224) 모델에서는 타일이 토큰을 아낀다. [원문] GR00T N1은 학습 때 "concatenating the views as a 4-grid video"(보조 에이전트 확인). 그러나 Qwen3-VL은 원본 해상도라 타일로 아낄 것이 없고, 여백·크기 불일치로 토큰이 오히려 늘어난다(399 대 356+4).
- [실측] HWt N=4 p95: 0.279(부하 오염) / 0.185(반복) — HW(0.181)와 같거나 느림. 또 카메라 경계가 이미지 안에 숨어 SFT가 "어느 칸이 손목인지"를 배워야 한다.

### (c) 시각 토큰 줄이기
- [원문] VisionZip(2412.04467, CVPR 2025, **기간 밖, 기초 문헌**, HIGH): "improving the prefilling time by 8x", 이전 방법보다 "at least 5% performance gains". FastV(2403.06764, 기간 밖) 같은 층 안 가지치기. VLA 쪽 VLA-Cache(2502.02175, NeurIPS 2025, 기간 밖 — 처음 게시 2025-02-04, MED–HIGH): 프레임 사이 변하지 않는 토큰 재사용 "up to 1.7x speedup in CUDA latency", 성공률 손실 "negligible". SmolVLA(2506.01844, 기간 안, MED — HF LeRobot): "limiting the visual tokens to 64 per frame". GR00T N1(2503.14734, 기간 밖 처음 게시 2025-03-18, HIGH): "224×224 followed by pixel shuffle, resulting in 64 image token embeddings per frame".
- **우리에게 맞지 않는 이유 [추정]**: 가지치기·병합 방법은 모델 내부 수정이라 vLLM 표준 서빙·배치 불변 모드·접두 캐시(이미지 해시 기반)와 바로 맞물리지 않는다(각 논문에 vLLM 호환 언급 없음 [미확인]). 그리고 **우리 병목은 토큰 수가 아니다**(§1 해석). 가장 싼 손잡이는 **해상도**(요청별 `mm_processor_kwargs`)이고, 이것도 지연 이득이 작았다(HWh 0.218–0.273, HhW 0.157–0.183).

### (d) 캐시·재사용 — **핵심**
- 호출 안(8 시퀀스): 접두 캐시가 `[system][images][state]`를 공유해야 한다. 동시에 들어간 시퀀스끼리는 아직 계산 안 된 블록을 공유하지 못한다 → **lead**(선행 1개가 접두 KV·인코더 출력을 만들고 나머지 7개가 재사용). [실측] N=4 p95: H 0.266 → 0.175, HW 0.290 → 0.280(첫 판, 부하 47–57) / 0.530 → 0.181(반복 판).
- 호출 사이(0.33 s 간격): 머리 프레임은 로봇이 움직이면 매번 달라져 해시가 달라진다 → 재사용 불가. **머리 고정 상한(hstatic)**: HW N=4 p95 0.290 → 0.236(부하도 낮았음) — 이득이 작고, 낡은 머리 프레임을 쓰는 위험(선점 판단 오류)이 커서 권하지 않는다.
- 이미지 순서: 호출 사이에 바뀌지 않는 system·질문 정의를 앞에 둘수록 좋지만, 상태가 매번 바뀌므로 호출 사이 재사용은 system 수준뿐이다.
- 캐시 끔 [실측]: `--no-enable-prefix-caching --mm-processor-cache-gb 0`에서 HW N=4 p95 **0.628 s**, H 0.544 s — 캐시가 지연의 절반 이상을 떠받친다. 실물 서버도 반드시 켠다.

### (e) 카메라별 해상도 배분
- [실측] 손목 28 토큰(HWh)은 이득 없음. 머리 112 토큰(HhW)은 첫 판에서 가장 빠른 머리+손목 배치(leadref 0.157)였지만 반복 판에서는 HW와 0.006 s 차이.
- [우리 접목] 해상도는 지연이 아니라 **정확도 실험의 변수**로 둔다. 머리는 0.77 m 거리 전경, 손목은 7–50 cm 근접이라 손목을 줄이는 것은 §57 근거(cm 이하 정렬)를 깎는다. 기본은 둘 다 원본.

### (f) VLA들이 하는 방식
| 모델 | 뷰 | 해상도·토큰/뷰 | 합치는 법 | 날짜·신뢰도 |
|---|---|---|---|---|
| π0 (2410.24164) | 로봇별 2–3장(예: 양팔 UR5e "three camera images") | 해상도·토큰 논문 본문 [미확인](PaliGemma 224 → 256 토큰으로 알려짐, 미확인) | 이미지별 인코딩 후 언어 토큰과 같은 공간으로 투영해 이어붙임 | 기간 밖, HIGH |
| π0.5 (2504.16054) | 손목 2 + 앞 1 + 뒤 1 | [미확인] | "We use all four cameras for high-level inference, and the wrist and forward cameras for the low-level inference process." | 기간 안, HIGH |
| OpenVLA-OFT (2502.19645) | ALOHA "three camera viewpoints (one top-down, two wrist-mounted)", 224×224 | "256 patch embeddings per view" | 뷰별 인코딩, 공유 투영, 이어붙임; 뷰 2배 → "256 to 512" 토큰에도 "0.112 sec" | 기간 밖(2025-02-27), RSS 2025, HIGH |
| GR00T N1 (2503.14734) | RoboCasa 좌·우·손목 3장, GR-1 머리 1장 | 224×224 → 64 토큰 | 뷰별 64 토큰 | 기간 밖(2025-03-18), HIGH |
| SmolVLA (2506.01844) | top·wrist·side 3장 | 64 토큰/프레임(pixel shuffle) | 뷰별 | 기간 안, MED |
| Gemini Robotics (2503.20020) | 카메라 구성 본문 [미확인] | — | 백본 "query-to-response latency ... under 160ms", 전체 "approximately 250ms" | 기간 안, HIGH |

공통점: **뷰마다 따로 인코딩해 토큰을 이어붙인다**(우리 (a)와 같음). 차이: VLA는 뷰당 64–256 토큰으로 낮은 해상도를 쓴다 — 우리 머리 252·손목 104 토큰은 이 범위 안이다. π0.5는 상위(결정) 추론에 카메라 4대를 **모두** 쓴다 — 결정층에 손목을 넣는 §57과 같은 방향.

## 3. 손목캠 효과 근거 (질문 2)

| 출처 | 수치 | 신뢰도·기간 |
|---|---|---|
| OpenVLA-OFT LIBERO 표 I (같은 "modified" 데이터) | 제3자 시점만: Spatial 96.2 / Object 98.3 / Goal 96.2 / Long 90.7 / 평균 **95.3** → + 손목 + 고유감각: 97.6 / 98.4 / 97.9 / 94.5 / 평균 **97.1** | HIGH, 기간 밖. 손목과 고유감각이 함께 바뀌어 손목 단독 기여는 분리 안 됨. 긴 과제(Long)에서 차이가 가장 큼(+3.8) |
| Hsu 외 "Vision-Based Manipulators Need to Also See from Their Hands" (2203.12677, ICLR 2022 oral) | 손목 시점은 "consistently improves training efficiency and out-of-distribution generalization"; 손목만으로 부족할 때 제3자 시점이 필요하지만 "also harms out-of-distribution generalization" | HIGH, 기간 밖, 기초 문헌 |
| π0.5, GR00T N1, SmolVLA, OFT ALOHA | 손목캠을 기본 입력으로 쓰지만 손목 절제 표 없음 | 설계 관행 근거일 뿐 |

- **기간 안의 손목 절제 수치는 이번에 확인하지 못했다**(검색 한도). 근접·접촉 구간에서 손목이 가장 중요하다는 정량 근거도 [미확인].

## 4. 권고 (질문 3) [우리 접목, Claude 판단]

### 4.1 입력 배치
- 순서: `system` → `"head camera:"` + 머리 672×376(252 토큰) → `"<right|left> wrist camera (active arm):"` + 활성 손목 424×240(104 토큰) → (양팔 스킬이면 두 번째 손목 + 표지) → 상태(S1 1 mm) → 질문. 이미지 토큰 합 **≈ 360**(양팔 ≈ 466). 해상도 설정은 모델 기본값 그대로(요청별 kwargs 없음 → 학습·서빙 불일치 위험 제거).
- 타일·토큰 가지치기는 쓰지 않는다. 손목 저해상도는 정확도 실험의 절제 조건으로만.
- `question_id@vN`에 카메라 구성 문자열을 넣는다(예 `cam=H672x376+Wact424x240`) — §57 영향 항목과 같음.

### 4.2 클라이언트 (지연)
- `JevLClient.acall`을 **lead 계열**로 바꾼다: 첫 갈림 노드 시퀀스를 먼저 보내고 응답 뒤 나머지를 병렬로. 뒤 시퀀스에 uuid(내용 해시)를 붙이고 바이트를 뺄지(leadref)는 다음 사전 등록 판에서 정한다 — leadref는 처리기 캐시가 밀려나면 요청이 실패할 수 있으므로 실패 시 바이트 포함 재전송이 필요하다.
- 예상 H200 N=4 p95: **0.18–0.21 s**(부하 낮을 때, 합성 754 토큰·1,267 토큰), 부하 오염 판 최대 0.28 s. 사전 문턱 0.33 s와 목표 0.15 s 사이. 실제 DEV 프롬프트(824 토큰)는 두 판 사이 길이다.
- 더 줄이려면(이미지와 무관): 한 호출 8 시퀀스를 줄이는 것(보기 이름 첫 토큰을 모두 다르게 해 질문당 1 시퀀스 = 5 시퀀스) — `dir_xy`의 `plus_*`/`minus_*` 공유 첫 토큰이 갈림 노드 5개를 만든다.

### 4.3 SFT와의 관계
- **학습도 같은 배치로**: 같은 순서·표지·해상도·질문 판본. 비전 타워 동결(§52)이라 이미지 토큰 수가 고정되어 학습·서빙이 일치한다.
- [가정] 손목 이미지 무작위 빼기(예: 15 %, 표지는 "wrist camera: unavailable")를 넣으면 §57 절충안(근접·접촉 구간만 손목)이나 손목 프레임 누락 때 같은 모델을 쓸 수 있다. 쓸지는 §57 결정 실험 조건에 넣어 정한다.
- 활성 팔은 계약의 `arms`로 정하므로 학습 데이터에서도 같은 규칙으로 슬롯을 채운다. 우손목만 풀에 있으므로(§57) 왼팔 스킬 데이터는 새로 모아야 한다 [확인 필요].

### 4.4 M4 겹침 호출
- N=4는 M4 겹침 호출 동시성 상한에 해당(`N_max = ceil(d_p95/T_c)+1`). lead는 호출마다 선행 한 번이 직렬로 붙지만(N=1 p50 0.074–0.08 s) 폭주를 없애 N=4 꼬리를 줄인다. 호출 시작을 0.33 s 격자에 엇갈려 보내는 M4 방식은 동시 도착을 더 줄이므로 lead와 같은 방향이다.
- 머리 프레임 재사용(hstatic)은 권하지 않는다 — 이득 작고, M4 (b) "예상 대 측정" 판단이 낡은 영상에 걸린다.

### 4.5 실물 서버(RTX PRO 6000, §49)
- H200 수치는 옮길 수 없다. [추정] 이 GPU는 메모리 대역폭·BF16 연산이 H200보다 낮아 GPU 쪽 prefill이 더 느리지만, 우리 병목은 CPU·요청 수 쪽이므로 서버 CPU가 좋으면 차이가 줄 수 있다 — 실측 전 [미확인].
- 같은 `jevl_mmbench.py`를 그 서버에서 H, HW(lead/base) × N=1/4로 먼저 돌리고, 로봇↔서버 LAN 왕복과 JPEG 인코딩 시간을 더한다. 카메라 → 서버 경로에서 JPEG(q90, 머리 32 KB·손목 10 KB)로 보낸다(기존 PNG 280 KB보다 훨씬 작다).
- 파드처럼 CPU를 다른 작업과 나누지 않도록 vLLM 서버 CPU 코어를 따로 잡는다.

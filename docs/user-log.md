# 사용자 발언 기록 (시간순)

사용자가 대화에서 말한 지시와 정보를 빠짐없이 옮긴 기록이다. 음성 입력이라 원문에 오타가 많아서, 뜻을 그대로 살려 정리했다.
새 세션은 이 파일을 보고 사용자의 의도를 파악한다. 새 발언이 생기면 아래에 계속 덧붙인다.

1. 저장소 정리

   - 저장소에 있던 논문(PDF)은 모두 지운다.
   - 이름 변경은 나중에 사용자가 직접 한다.
2. 브랜치
   - `dev` 브랜치를 만들어 모든 작업을 `dev`에 올린다.
   - 사용자가 확인한 뒤 `dev`를 `main`에 반영한다.
   - 푸시해 달라고 하면 `dev`에 자동으로 푸시한다.
3. 대주제
   - 요즘 GPT Astra(GPT-6 Astra)로 로봇을 명령 제어하는 프로젝트가 많다.
   - 물체를 보고 스킬을 생성해서 잡는 방법들이 많지만 실패할 때가 있다.
   - 실패할 때마다 Astra가 개입해서 진행하는 방식을 원한다.
   - 논문으로 제출할 계획이다. 컨트리뷰션은 아직 없고 점차 잡아간다.
4. 파이프라인
   - 사용자가 명령을 내리면 Astra가 명령을 잘게 쪼개 어떻게 실행할지 미리 계획한다.
   - 계획에 맞는 스킬들을 불러와서 Astra가 진행한다.
5. 진행 확인: 프레임별로 확인해서 Astra의 계획대로 되고 있는지 판별한다.
6. 계층 구조
   - Astra의 문제는 API라서 시간이 너무 오래 걸린다는 것이다.
   - Jev(TypeSafe AI, 새로 나옴)는 객관식 문제를 엄청 잘 푼다.
   - Astra로 조정하는 방식이 VLA보다 생각보다 성능이 잘 나오지만, 결국 이미지를 보고 엔드포인트로 움직이는 방식에 그친다.
   - Jev를 쓰면 엔드포인트를 어디로 얼마만큼 움직일지에 대한 순간적인 판단이 몇십 배 빠르다.
   - 예전 VLA에서 상위에 큰 LLM, 하위에 작은 VLM을 둔 것처럼, 상위에 Astra, 하위에 Jev를 둔다.
7. Overleaf 초안 (처음 규칙)
   - 사용자가 말한 것과 코드로 확인된 사실을 Overleaf 형식으로 주기적으로 업데이트한다. 나중에 복붙만 하면 되게 한다.
   - 처음부터 완벽할 수 없으니 천천히 쌓는다. 논문 형식이 아니라 마인드맵처럼 "이렇게 할 거다"를 적는다.
   - 이상한 글이 들어가면 안 된다. 정해지지 않은 건 언급하지 않는다. 사용자 머릿속에서 나온 결과여야 한다.
   - → 8번과 16번에서 개정되었다.
8. Jev 정보: 최근 일주일간 인터넷 자료를 찾아보면 알 수 있다고 했다(조사 완료).
9. 주의사항 기록: 대화 중 주의사항이나 제약은 반드시 MD 파일로 남긴다. 특히 자율로 맡겼을 때 이를 계속 참고하고 어기지 않는다.
10. 빈 곳 논의 요청: 큰 틀 사이사이를 효율적으로 연결하는 부분, 즉 컨트리뷰션 거리가 부족하니 논의할 거리를 정리해 달라고 했다.
11. 방향 지시 (모듈별)
    - (1) 이미지→텍스트: Jev는 이미지를 못 본다. LLM/VLM/VLA 논문뿐 아니라 텍스트와 이미지를 제대로 변환하는 다른 분야 연구에서 가장 효율적인 방법을 찾는다.
    - (2) Astra→Jev 전달: 1번과 거의 같은 문제다. Astra는 이미지를 보고 명령하지만 Jev는 아니니, 효율적으로 전달하는 방법을 더 생각한다.
    - (3) 행동: 촘촘하게 가도 된다. Jev 방식이면 충분히 가능하고 할 만하다고 본다.
    - RTC 적용
      - 1초에 Jev를 한 번이 아니라 3번 정도 계단식으로 겹쳐 쓴다.
      - 겹치는 부분의 움직임이 제대로 반영됐는지 스스로 감지하고 업데이트하는 시스템이 자동으로 있어야 한다. 이게 굉장히 중요하다.
      - Jev가 빠르다지만 로봇 동작에서는 빠르지 않으니, 연속 동작처럼 내뱉게 하는 법을 RTC에서 많이 참고한다.
    - 두 단계: 먼저 RTC와 유사한 방법, 다음으로 액션 스무딩이나 VLA에서 쓰는 부드럽게 하는 방법으로 아주 작은 움직임을 처리한다.
    - 스킬
      - 기존 스킬도 Jev와 엄청 연관될수록 좋다.
      - 1년 이내에 나온 GitHub 스타 상위 5개 중에서, LLM이 스킬을 불러오고 끝이 아니라 잘게 엮어 놓은 논문을 참고해 파이프라인을 대충 짜 본다.
    - (5) 진행 판별
      - VLA에서 "계획대로"를 무엇으로 정의했는지 많이 참고한다. VLA는 로봇을 학술적으로 조종하는 개념 공부를 많이 해 놓았다.
      - 하지만 VLA의 엄청난 단점은 다른 환경에 가면 일반화가 안 된다는 것이다. LLM은 일반화가 된다. **이걸 엄청 부각하고 항상 기억한다.**
    - (6) Astra 호출
      - 적어도 실패 판정이 났을 때는 Astra를 부른다. 그 순간 한 장이 아니라 연속 프레임을 준다. 예: 이미지 하나에 사진 10개.
      - 호출 방식은 비교 평가한다: Hz 단위 주기 / 정해 둔 필요한 순간마다 / "이때쯤 결과가 나왔어야 하는데 안 나오네"라는 자체 판단.
      - VLA에서 실패했을 때 어떻게 되돌아갈지 정하는 프레임워크를 참고한다.
    - (7) 복구: VLA에서 가장 좋은 실패 복구 방법을 찾는다. 논문은 무조건 1년 반 이내.
    - 정지: Astra가 처음 생각할 때는 멈추는 게 맞지만, 그 이후는 웬만하면 멈추지 않는다. 실패로 생각해야 하는 경우만 어쩔 수 없다.
    - (9) 경험 축적
      - 경험 축적이 제대로 되어야 한다.
      - API로 불러오는 모델의 경험 축적을 어떻게 하는지, 어떻게 해야 효율적인지 논문을 찾는다. 1년 반 이내.
    - (10) 평가 비교 대상: Astra만 / Jev만 / VLA / 룰베이스(스킬 다발) / LLM+스킬을 연결한 기존 논문 / Astra를 쓰는 기존 논문
    - (11) 안전은 크게 다루지 않는다.
    - 완벽한 계획을 제대로 짜고 모두 기억한다. 계획 초안을 Overleaf에 올린다. 사용자가 말한 내용이 사용자가 의도해서 적은 글로 보여야 한다.
12. 초안 조사 단계
    - 약 3시간 동안 엄청 꼼꼼하게 한다.
    - 틀린 건 없는지, 정말 최고 성능인지, 저자 블로그까지 뒤진다.
    - "마차를 이어서는 기차를 만들 수 없다." 처음이 틀어지면 아무리 고쳐도 좋은 게 안 나온다.
    - 끊임없이 스스로를 의심하되, 과한 의심으로 할루시네이션을 일으키지 않는다.

13. 상세 설계 단계

    - 꼭 MD로 기억해 둔다.
    - 시간은 정확히 맞출 필요는 없지만 ±1~2시간 안이어야 한다.
14. 신뢰도 기준

15. 분야: 정답이 로봇 분야에서만 나온다고 생각하지 않는다. LLM/VLM 분야의 방법이 로봇에 오기까지 시간이 걸리니, LLM, VLM, 로봇, VLA 전방위로 보고 최고의 모듈을 만드는 데 집중한다.
